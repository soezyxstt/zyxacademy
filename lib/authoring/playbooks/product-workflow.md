# Zyx Product Bundle V4: Workflow and Contract Playbook

## 1. Stage objective and compatibility

Create new Article/Diktat products as `product-bundle.v4`, `article.v4` and `diktat.v4`. V2/V3 remain readable and their existing validators remain available for explicit legacy revisions. Keep an existing bundle's version when revising it unless the operator requests a reviewed V4 conversion. A V3-to-V4 conversion reconstructs ordered parts and Diktat lineage; changing a version marker is insufficient.

For a standalone Pembahasan soal learning product, use `product-bundle.v5` with `productType: "solution_collection"`, product `schemaVersion: "solution_collection.v1"`, and nested collection `schemaVersion: "solution_collection.v1"`. Follow the V5 schema documents and semantic rules returned by `workflow.get_contract`. Do not fabricate an Article or Diktat to accompany it. V2 to V4 retain their profile-specific evidence gates and now use the same exact-revision, explicit review requirements through Admin and MCP. Assessment questions and their protected answers belong to `quiz_bank` or `reference_question_ingest`, never to a new Product Bundle. An authorized admin may publish reviewed learning products explicitly through scoped MCP or the Admin UI.

Each standalone example must be suitable for learner release independently of an assessment. Record separate, precise provenance for the problem and the solution, including source locators and rights or release evidence required by the active schema. Do not copy or infer a protected assessment answer, even when the problem itself is visible. Unknown provenance or release eligibility blocks release. Review every item for correctness, reasoning, both provenance records, and release eligibility against the exact current bundle checksum; changed content needs a new review. Never publish these products into public search, quiz or Zyra indexes.

Organize each example according to its problem type and discipline: preserve relevant givens, choices and answer format where applicable, show justified steps and assumptions, and verify the result with units, conditions or domain-specific checks. Do not force unrelated disciplines into a single numerical derivation. Use the supported Article parts and validated visual capabilities when they help explain the reasoning.


## Existing-content revisions, V3 and later

For edits to existing content, use the flexible revision tools advertised by the current workflow contract. This path supports Idea V3 and learning Product V3/V4/V5 only; do not create compatibility work or convert a bundle below V3 implicitly.

1. Obtain the current compatible stage bootstrap, then call `authoring.get_edit_context` with the import and exact observed revision. During drafting, use `responseMode: "compact"` and `target` to read one stable entity, section, block or Diktat unit (`unitId`). Request full context for source/reasoning review and final readiness.
2. Call `authoring.create_revision` to fork a live artifact or editable draft into a durable draft. The old publication stays live. Existing source evidence supplies the edit scope; no new Source Pack or expired original run is required. Use the returned draft execution identity for applicable trusted V4 verification.
3. Call `authoring.patch_revision` with bounded set/add/remove/move operations addressed by stable IDs and `responseMode: "compact"`. The server rebuilds hashes and the ZIP. Continue with the returned successor import ID and revision after every accepted edit. Compact replies defer review/readiness; they never mean approval. A stale revision requires rereading and explicit reconciliation, never a blind retry with a substituted checksum.
4. Call `authoring.plan_release` with the exact draft entries. A release can refer to multiple Idea and Product artifacts and profiles. Inspect changed units, preserved evidence, affected dependents, current blockers and next actions. Changed derived content still needs its applicable trusted verification; no receipt is synthesized.
   For V4 referencing changed Ideas in the same release, call `authoring.prepare_revision_verification` with the exact mixed entries before running the trusted operator. The server binds its prospective Idea graph to admitted artifacts and the current live baseline. Changing an entry requires a new context and verification. Source documents and excerpts remain admitted, active canonical evidence; new source ingestion follows its source-grounded workflow.
5. Independently review the actual changed content and affected reasoning or source context. Submit the explicit profile-specific evidence through `authoring.review_revision`. Reuse only the server-confirmed unchanged decisions attributed to the same reviewer; do not approve unseen changed units.
6. Replan after review and verification. With explicit publication authorization and `authoring:publish`, call `authoring.publish_release` using the exact manifest entries and plan hash. Atomic replacement must leave the previous live release intact on failure. No Admin website visit is required.
7. Use `authoring.list_revisions` for history. `authoring.restore_revision` creates a new draft from historical authored content against the observed current baseline. Restoration never publishes automatically or rewrites historical artifacts; follow the same plan, evidence, review and publication steps.

Initial source-grounded authoring uses the typed draft path below when advertised. Existing-content edits keep the revision workflow. Runtime schemas are authoritative; if these tools are absent on an older server, report the missing capability and follow its advertised archive contract.

For a derived Diktat, inspect affected units and their exact source references. `derivedContentReviews` may confirm unchanged units against the current Article hash with real review notes and `authoring:review`; partial reviews cannot clear other units. If print proof disappears or runtime changes after sealing a draft, use the advertised `refreshPrintEvidence: true` with `operations: []` to obtain the needed successor print version. Do not make fake content edits to clear either blocker. These paths retain current verification and release approval.

## 2. Bootstrap, scope and upstream gate

1. Call `workflow.get_playbook` for `zyx-product-bundle-mcp`, stage `product`, with actual host capabilities. Independent Critic and Student POV subagents are required.
2. Start or resume `idea_product` with the selected course, chapter, validated Source Pack and bootstrap token. Fetch `workflow.get_contract` before authoring and after contract drift.
3. Read `productBundle.initialDraft` only when advertised by the connected server. For its supported products, fetch `productDraftInput` from `productBundle.schemaDocuments` once per pinned descriptor; retrieve other schemas as the content requires. Verify response bytes against `sha256`, reuse matching local copies, and refresh the contract on HTTP 409 or drift. The archive path uses the full manifest and entity schemas. `productBundle.pilot` remains a compatibility alias.
4. Read published Ideas, learning sections and active source excerpts. Inspect existing imports/products to avoid duplicate drafts. Referenced Ideas and learning sections must be published before Product staging.

For V5, fetch `productBundle.solutionCollection.schemaDocuments` and use its dedicated review and release gates. The V4 Article, Diktat, PDF and verifier instructions below apply only to V4, not to standalone collections.

Completion: the run scope, current contract, exact schemas, source anchors and published Idea versions/hashes are known. If a server only advertises a legacy default, report the contract mismatch before creating new V4 content.

## 3. Author and independently review

1. Record representation choices outside the ZIP: objective, relationship to understand, chosen representation, reason, learner action, expected observation, formative check and source anchors.
2. Include only the requested products. When authoring an Article, build it with nonempty `sections`, empty top-level `blocks`, and ordered `parts` in every section block. Use `product/editorial` for mathematics, visuals and reasoning. A supplied block `contentMarkdown` must equal the projection of parts; omit it when allowing server derivation.
3. When requested, author Diktat `units` from published Ideas and source excerpts. Preserve Idea coverage, essential formulas, conditions and method choices. Standalone Diktat uses `ideaIds` and printable `parts`, with optional directly printable visuals. For a derived Diktat, typed input supplies `sourceArticleId` for an explicitly identified Article in the same request and exact unit `sourceElementRefs`; the server derives Article version/hash and dependency. Canonical archives require all three Article lineage fields and the locked dependency. Each top-level visual_ref requires staticMarkdown; snapshot pins are server-derived or must match exactly. Diktat contentMarkdown must equal the official units projection.
4. When requested, build atomic flashcards using `product/flashcards`. Every flashcard links to exactly one published Idea with weight 1; Article, Diktat and set Idea weights sum to 1.
5. When a checkout is available, use `bun run authoring:preview --input /absolute/path/draft.json --check` for structural preflight without a browser. Render with `--out` or `--watch` only when an optional visual inspection is requested. Screenshots, page images and visual inspection are not V4 review or publication prerequisites. Preview does not check live references, grading, code execution or saved progress and cannot issue a trusted receipt.
6. Send the same authored content to independent Critic and Student POV subagents. For the typed draft path, review the draft JSON before staging, then inspect the exact server-generated revision before approval. Apply required revisions and obtain rereads of the final revision. Keep review records outside the ZIP.

Completion: ordered parts, local references, lineage, mathematical meaning/conditions and source coverage are complete, and both reviewers have checked the final revision. Schema success alone does not prove readability or mathematical correctness.

## 4. Package, validate and stage

For new Article, Diktat, flashcard/set or standalone V5 collection without binary document assets or external Article lineage, prefer `authoring.create_product_draft` when advertised. Send `runToken`, `bootstrapToken`, a stable `draftKey`, and `draft: { products: [...] }`. Author content, Idea IDs and source/excerpt IDs. Optional `ideaLinks` preserves weights and roles for exactly those Idea IDs, while versions and hashes stay server-derived. The server assigns missing mechanical IDs, binds current published references and computes projections, dependencies, hashes and ZIP bytes. Supply stable IDs when another element refers to them. The request allows at most 256 products, including at most 16 Articles/Diktats, within 512 KiB; canonical validation and staging still apply.

For flashcards, send `front`, `back`, optional `explanation` and one Idea; atomicity is mandatory. A set supplies `title` and optional `cards`; omitting `cards` derives membership from cards with its `setId` in the same request. Standalone cards and empty sets remain supported. For V5, send exactly one `solution_collection` with `title` and `items`. The server fills collection identity, current active course/chapter titles and mechanical item/part/step IDs. Option IDs remain explicit for answer references. Provenance, correctness and release decisions remain authored and reviewed. V5 cannot mix with V4 products, runnable code or protected assessment content. Local draft preview currently renders Article/Diktat; inspect other profiles through staged product preview.

Keep the same draft key, run token and unchanged payload for a lost-response retry after checking available status. A successful create_product_draft already validates and stages through the canonical service; do not submit its artifact again. Use the returned import/checksum with revision tools. A changed payload cannot silently replace that draft. The in-repo injected-transport helper `lib/authoring/product-authoring-client.ts` carries successful successor identities for code agents; it is not an installed SDK and never retries writes, approves review or publishes.

The archive path remains available for admitted binary assets and Diktat lineage pointing outside the request. The ZIP packaging and validate/submit steps below apply to archive input only; both paths continue with exact staged context, verification and review. If an initial draft has no revision lineage, fork it with `create_revision` before patching; follow its returned `nextActions`.

For an existing V2 learning-only draft, pass `replaceImportId` and its last-read `expectedRevision` to `authoring.validate_product_bundle`, using the same verified run and bootstrap as restaging. This explicitly scoped recovery remains available when the structured-reader flag is active; new V2 submissions remain blocked.

The ZIP contains `manifest.json`, `entities/products.json` and `entities/dependencies.json`. Follow the manifest and entity schemas delivered by the contract, including entity-file and bundle checksums. Use the official projection/checksum helper when available; do not invent a serialization algorithm. Keep tokens, credentials and storage delivery URLs outside the ZIP.

1. Call `authoring.validate_product_bundle` with runToken, bootstrapToken, filename and bundleBase64. Resolve deterministic content errors until valid is true.
2. With staging authorized, submit a new draft or restage the existing import. Staging does not publish learner content.
3. Call `authoring.get_product_review_context` with the run, bootstrap, import and exact checksum for staged content, hashes, rubric and section references. Read `authoring.get_import` for current readiness. Missing verification, review or PDF evidence prevents publication where required.
4. If the unchanged draft was staged through Admin and its `stagingRunId` differs from the current run, an authorized active admin can call `authoring.adopt_product_draft_run` with that observed ID as `expectedStagingRunId` and the exact checksum. Fetch context again. Adoption is audited and invalidates prior PDF, verification and bundle review, so repeat them before publication.

## 5. Logic verification, final PDFs and exact-revision approval

For later withdrawal, read the published import and use `authoring.withdraw_product_bundle` with its exact `expectedRevision`, the bound `runToken` and fresh `bootstrapToken`. If that run expired, explicitly set `recovery: "exact_import"` and omit `runToken`; the exact import, checksum, validated course, active principal and session-bound bootstrap remain required. This withdrawal-only recovery needs no Source Pack and grants no review or publication capability. The Admin website is optional.

1. Request `authoring.verify_product_bundle` with `purpose: "logic"`, the default, for the exact content and current logic plan. It checks structure, references, notation, schemas and supported models without browser, PNG or PDF work. Read `authoring.get_verification` with the same purpose and plan hash. A `not_started` or changed plan needs a request for that purpose, not polling or content edits. Read `productBundle.verification.execution` for this browser-free server job. The server derives the checks; an author's matrix cannot remove them. These checks do not prove arbitrary mathematics or replace semantic review.
2. Independently review the exact content, source references, derivations, units, assumptions, model bounds and answers. With review authorized, submit the complete eight-criterion review, exact expectedRevision, policyVersion, contentFingerprint, current logic verificationPlanHash and verificationReceiptSignature, plus an explicit semanticHash decision for every included Article section. Use document anchors and omit section decisions if there is no Article. Optional visual checks remain untested unless performed and never block this V4 content review.
3. When final Diktat PDFs are needed, explicitly request `purpose: "pdf"` and follow `productBundle.verification.pdf.execution`. Read that separate print plan through `get_verification` with `purpose: "pdf"`; do not reuse a logic plan hash. The server checks exact canonical PDF bytes and current lineage and reuses unchanged authenticated targets with matching runtime. Only changed or unusable targets need new artifacts. PDFs retain the 1 to 4 page A4 profile and 10.5 pt body without auto-shrink. No screenshots, page captures or visual inspection are required. Article-only bundles need no PDF. Do not render on each content edit.
4. Read currentReadiness at the release boundary. V4 publication requires the current logic receipt and semantic review, plus current canonical PDFs for every included Diktat. An admin with `authoring:publish` may explicitly call `authoring.publish_product_bundle` with the same run, bootstrap and checksum. The server repeats these gates and rejects stale revisions. Report the import ID, revision and remaining blockers.

Completion: current logic verification and authored semantic review match the revision; any included Diktat has its canonical current PDF; currentReadiness reports publicationReady. Optional previews, screenshots and visual inspection are outside these gates. Never report an unperformed visual check as passed or an agent-authored report as a trusted receipt.

The preceding logic/PDF split applies to V4 only. V2/V3 learning-only revisions retain their legacy PDF and review policy. Use the scoped context and exact checksum. Article approval requires the current policy, fingerprint and complete anchored rubric, plus a semantic-hash decision for each existing section. Every legacy Article retains its PDF gate, using a linked Diktat or direct Article-only export. For bundles without Articles, decide the whole bundle without fabricating sections. Discover `productBundle.legacyLocalOperator` for the exact eligible target, deployed source revision, original staging run and active admin. Inspect its genuine PDF and page images before legacy review. It does not issue a V4 receipt. Do not apply this legacy rendering requirement to V4 or convert a legacy bundle implicitly. V2 assessment products remain excluded.

## 6. V5 standalone collection review

After staging, inspect the learner rendering and every example, including its problem, answer, reasoning, and separate provenance. Call `authoring.get_solution_collection_review_context` with the last-read checksum as `expectedRevision` for the exact revision and item hashes, then `authoring.review_solution_collection` with every item's correctness, reasoning, separate provenance and release decisions. Read `authoring.get_import` for current readiness. With `authoring:publish` and the same admin identity, explicitly call `authoring.publish_solution_collection` with that exact checksum. A retry with the same revision is idempotent; stale revisions fail. Report missing or stale decisions and leave the draft unpublished. V4 section, PDF and verification receipts do not substitute for V5 item review.

For V5, author optional `hintMarkdown` separately from the solution strategy. Keep it short and spoiler-free, without an answer, selected option, complete derivation or solution code. Every item review explicitly decides all five fields: `correctness`, `reasoning`, `problemProvenance`, `solutionProvenance`, and `release`. The reasoning decision checks the hint when present.
