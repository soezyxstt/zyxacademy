## Scope and access

The intended feature is always-on structured questions and answers, with no discussion feature flag. A question has an open or resolved thread, explicit answers and contextual replies. Active students, tutors and admins can use the global channel. Course channels require current full content access; a preview alone is insufficient. Course-scoped tutors also need the applicable assignment. Canonical and legacy course identities must agree or access fails closed.

Technical and academic team channels are private to their requester and authorized staff. Technical channels admit admins; academic channels also admit tutors, with course assignment and entitlement checks when a course is specified. Reads, writes, mention candidates, forwarded sources, attachments and notification visibility recheck access. Mentions are limited to ten eligible members per message. Forwarding stays inside a private channel, within the same course audience, or from global to an authorized course; it cannot move a private message outward. Forwarded source access is checked again when read.

Students need PKA registration to join PKA course discussions; admins and assigned tutors do not need a student registration. Authenticated legacy accounts without a canonical identity can be provisioned atomically. An existing identity without any role remains denied: the stored rows do not distinguish interrupted provisioning from deliberate role revocation, so neither discussion access nor the shared course resolver restores a legacy role automatically. Fresh legacy identities and their initial roles are created in one transaction; a request that loses the identity-creation race cannot add a role. Existing roleless identities require an authorized account repair, even if an earlier partial write caused them.

Authors can edit their own human messages for less than five minutes after creation. Admins can edit human messages beyond that window or moderate other authors' messages. Edits use a revision check. Authors and admins can delete messages; deletion is soft. The thread author or an admin can resolve and reopen a thread. Eligible participants can report another person's message, and admins can resolve or dismiss reports. Writes and reports are rate limited.

## Content and notifications

The discussion renderer supports a restricted Markdown subset, links, code and bounded math, including math inside emphasis and compact reply context. It does not render raw HTML or remote Markdown images. Attachments use a private authenticated endpoint, with inline viewing and download. Each message accepts at most four still JPEG, PNG or WebP images, each up to 8 MiB, 16 million pixels and 4096 pixels on either edge. Server decoding rejects invalid or animated images and strips metadata. Images over 1 MiB may be resized and converted to WebP when useful; smaller images avoid optional lossy compression, with lossless re-encoding when orientation requires it. New uploads also store a WebP preview up to 480 px and 128 KiB. The full image loads on opening or download; old rows without a preview show an openable placeholder. Both objects require current authorization and are covered by cleanup. Only the uploader can access an unattached ready image, and attached images require current access to the message. Storage keys are not returned to clients.

Mute is per user and channel. It suppresses new inbox and push delivery, including mentions, while thread unread counts continue to track messages. Reading advances a monotonic sequence watermark. Signed response receipts bind the viewer, thread, fetched message revisions and thread status revision; acknowledgments persist only the covered, visible message IDs. Notification clearing and delayed delivery use these accepted revisions, not transaction timestamps. A later-page read cannot acknowledge an unseen earlier edit. Older events without a revision deliver conservatively.

The dispatcher derives notification IDs from the event and recipient, traverses bounded recipient pages with durable progress, and rechecks channel access before inbox and push delivery. Atomic participant summaries avoid rediscovering all authors from message history for each event. Writers capture the participant sequence cutoff under the thread lock, including edits, deletion and resolution; fanout uses membership at that sequence rather than transaction-start timestamps. Pending legacy events without a cutoff restart participant discovery conservatively against current membership, access, mute and read checks; completed legacy events are not reopened. Token reads and push outcome writes are batched, and failed events use retry backoff. Push content does not include discussion text. Question, message, edit, deletion and resolution events notify eligible participants; reports notify eligible admins through the reports tab. An uncertain push acknowledgement can cause a duplicate push, while inbox IDs remain deterministic. Event writers capture validated mention snapshots in the mutation transaction, preserving queued mentions through later edits. Local service-to-worker regressions exercise both ordering boundaries.

## Rewards and appearance

Eligible students receive 5 base XP for a new question and 10 base XP plus 1 LP for an explicit answer to another person's question, subject to separate Jakarta-day caps of five questions and ten answers. Existing rank-based bonus XP applies. The outbox and reward keys make awards idempotent per student, reward kind and thread. Staff activity, self-answers, edits, contextual replies and forwards do not earn these rewards. Deleted evidence is ineligible before processing; an already paid award is not automatically clawed back. Discussion activity does not create course learning credits, checklist progress, badges, missions or qualified learning days. See [gamification](gamification.md).

The adapter defaults to the author's equipped, owned chat skin. The server also permits an explicitly selected owned skin after checking its catalog slot and inventory ownership, and stores only that skin ID on the message. Authorized participants can see it without receiving the author's inventory or private profile. A Zyra answer can inherit the invoking message's skin. Course chat's separate assistant-only appearance remains unchanged.

## Zyra and labels

An explicit Zyra request is recorded against the invoking author. The worker rechecks their access and active-assessment boundary, then constructs context from the question title, bounded to 160 characters and treated as untrusted content, the complete invoking message, up to 12,000 characters, and excerpts of at most five earlier visible messages, up to 2,000 characters each. Context and attachment identities are fingerprinted and rechecked before publication. Free-tier requests reject images on the invoking message, while keeping earlier text and omitting earlier images. Students in channels without a course use the Free policy even with a paid course; tutors and admins use the standard policy. The composer help explains the applicable scope. Eligible requests prioritize the invoking images and use remaining slots and bytes for recent earlier images, up to four total; excess earlier images do not block a text invocation. The prompt identifies omitted images and prohibits inferring their contents. Image requests also depend on the existing Zyra image capability and its byte limits. The request is configured with the invoker's identity and allowance, a stable idempotency key, cache bypass and one executor attempt. A stored result can be recovered after revalidation; an uncertain dispatched result is not automatically regenerated. Failure does not undo the human message.

Question creation enqueues a label request. Automatic labels currently use deterministic classification and retain an explicit help category; they do not debit a student's tutoring allowance. A session-authorized staff classification action can request AI classification under that staff member's budget, with a deterministic fallback. Fully automatic provider classification needs an application-owned operational budget identity, which is not configured by this change. Labels never widen staff access.

Discussion generation and staff classification use the shared executor's `singleDispatch` option with a stable idempotency key. This bypasses shared caches and disables provider fallback, SDK retries and structured-output repair for the invocation. Confirmed terminal HTTP failures on the router refund the application lease after complete provider-attempt settlement, without another dispatch. Ambiguous outcomes remain uncertain for reconciliation instead of being refunded and regenerated. Legacy single-dispatch HTTP failures remain uncertain because the same control-plane settlement cannot be verified there. Ordinary legacy callers can settle their own application lease after terminal HTTP 400/422 or an exhausted retryable chain only when every attempted failure is confirmed HTTP; any earlier uncertain attempt prevents that refund. Across ordinary and single-dispatch calls, timeouts and unknown billable outcomes stop automatic fallback. This deliberately trades immediate availability for avoiding a second provider charge after an unknown result. Reconciliation failures are also uncertain. The pedagogy harness and tutor RAG preserve that outcome and stop their own legacy-generation fallback, including requests without an idempotency key; shadow telemetry uses the executor and harness outcome contracts. The worker environment projection retains `ZYRA_CONTROL_PLANE_URL` and `ZYRA_CONTROL_PLANE_TOKEN` for the existing deployment filter. Local fake-provider tests exercise these boundaries; live provider accounting and deployed configuration are unverified.
