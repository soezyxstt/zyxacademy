# Product Bundle V3 Contract

Product withdrawal requires the caller-observed checksum at both the Admin API and shared service. The MCP tool additionally requires a fresh session-bound bootstrap and either a bound learning-product run or explicit `recovery: "exact_import"` without a run. Exact-import recovery validates the staged checksum and course and remains withdrawal-only, without a Source Pack or Admin website step. The write transaction locks and rechecks the import snapshot before retiring projections; retry uses the same checksum.

Status: `ACTIVE` behind `FEATURE_STRUCTURED_ARTICLE_READER_V1` for new submission and structured review. V2 remains readable during transition.

## Article structure

An Article V3 stores `sections` and has no flat root blocks. A section contains stable identity, kind, title, slug, order, optional parent, learning objective, Idea links, source references, and semantic blocks. `topic` requires exactly one `learningSectionId`. `overview` and `summary` may synthesize multiple Ideas without one learning section.

Each block stores `contentMarkdown`, `blockType`, optional title, Idea IDs, and source references as fields. Metadata is never embedded in Markdown. The compiler preserves block types in the semantic AST and derives `artikel.contentMarkdown` deterministically for compatibility, search, and vector indexing.

## Quality gates

- Every Idea is covered and traceable to a source.
- Every topic has a learning objective, core explanation, understanding check, and provenance.
- Examples, analogies, visuals, formulas, misconceptions, and warnings are required only when pedagogically relevant.
- Each topic declares a structured learning-time estimate for reading, examples, and practice. Completeness is judged against its objectives, not a fixed word count or reading-duration target.
- A chapter has overview, synthesis or summary, and a final understanding check.
- Pedagogy metadata binds objectives to explanation and formative-check blocks, declares prerequisites and symbols, and records whether a visual is required or not relevant.
- Formative checks are learning interactions only. `checkKind` supports `multiple_choice`, `short_answer`, `numeric_answer`, and `conceptual_explanation`. An optional typed `evaluation` uses `choice`, `text_exact`, `numeric`, or `ai_rubric` respectively. Without `evaluation`, the published check remains readable and reveal-only.
- `feedbackPolicy` is optional and may contain up to three progressive hints plus `allowRetry`. Evaluation and reveal routes authorize the published Article version and course enrollment, and never write attempts, grades, mastery, or assessment rows.
- Required visuals use typed, non-executable payloads. A mathematically sampled graph is explanatory evidence only and never replaces an analytic proof.
- Function plots may set `equalAxisScale: true` when geometric shape matters, such as circles and conics. This preserves the same display length per unit on both axes during zoom and pan. Included roots use filled markers; a hollow marker must not imply an excluded point when the function is defined there.
  Optional bounded `pointMarkers` identify excluded points (`open`) and defined values (`closed`), with finite coordinates, a label, and a valid series reference. Series may declare bounded `excludedX` inputs so sampling never joins branches across an undefined input or vertical asymptote. Static fallback must explain the same distinction.
  Embedded Article plots retain authored equations. Their fallback values are available through the keyboard-accessible "Nilai grafik" control rather than repeating a table below every graph; textual fallback remains available before the client renderer loads.
- MCP quality reports warn when a graph-relevant section has no linked visual, when one display formula joins multiple relations with commas, or when explanatory passages, worked-example steps, and verification repeat within a section. These warnings require editorial review; they do not prove a visual is always necessary or automatically rewrite content.
- Display formulas may use a short Markdown list with one relation per item. The quality count preserves mathematical inequalities such as `x<1` and does not mistake commas inside set notation for a crowded formula.

## Review, edit, and publication

`review_item_bundle` identifies `targetType` and `targetId`. V3 Article review targets `article_section`; the V2 block endpoint remains an adapter for `article_block`.

Admin edits require `expectedRevision`, accept only safe content fields, recompute generation hashes and bundle checksum, preserve approval for unchanged sections, reset changed section approval, and mark an Article to Diktat dependency `STALE`. Stable IDs, provenance, and lineage identity cannot be edited.

Publication requires the approving admin to decide every Article section and record the exact checksum, current full-bundle fingerprint, policy version and eight anchored rubric criteria. Approval requires every section approved. A different reviewer cannot reuse another reviewer's approval. Multi-Article bundles review every Article and linked Diktat, independent of file order, and require current PDF evidence for each pair. Missing or stale approvals, stale dependencies, failed visual contracts, and missing, failed, or stale Diktat PDF evidence block publication. Publishing is transactional and idempotent.

The Diktat PDF worker compiles the authored Diktat from the linked Article and Diktat revision into a fixed two-column print layout with 10.5 pt body text, 1.38 line height, 12 pt section headings, and formulas at 1.05 em. Formula groups stay together across page and column breaks. The readable-v3 profile preserves the 4-page maximum without automatic font shrinking. It separates formula groups from symbol lists, renders formulas fail-closed, repeats contact details, a clickable website link, and current/total page numbers in the footer. The print header spans both columns to prevent a blank first page; paragraphs stay together. It records renderer and print-profile identity, verifies a 1 to 4 page PDF, then stores revision-bound evidence outside the ZIP. Only transient renderer, timeout, and storage failures are retried. Admins may render, retry, and preview this artifact. Students may download the published PDF only when authorized for the course. The generic storage proxy cannot expose protected Product Diktat keys.

## Private local PDF operator for legacy drafts

This path is for an explicitly authorized operator using the verified production target and an exact V2 or V3 learning-only draft containing an Article, with or without a linked Diktat. Allowed products are Article, Diktat, flashcard set and flashcard. It rejects assessment products, V4/V5 content and other versions. V4 continues to require its trusted verification receipt. This command creates PDF evidence only. It does not approve or publish a bundle.

First obtain the deployed 40-character source SHA from the authorized deployment record. The operator checks that the local canonical repository is clean and at that SHA, but cannot independently discover the deployed SHA. From current review context obtain the import ID, checksum and the original run that last created or replaced that draft. The actor must be the authorized active admin, including both the current admin membership and the legacy admin role. Production database and private storage targets use the same guard as the V4 local operator. Do not execute against an unverified target.

If the staging identity belongs to an Admin upload or edit rather than the current MCP run, an authorized active admin may call `authoring.adopt_product_draft_run` with the verified product run and bootstrap, import ID, exact checksum and `expectedStagingRunId` from current review context. The transaction records both identities and invalidates existing PDF evidence, verification and bundle review. Fetch context again and use its new `stagingRunId`; perform fresh verification and review. The artifact and checksum remain unchanged. A changed draft, actor, scope or staging identity fails the claim.

Discover the installed and reviewed browser pins with `node scripts/authoring/run-product-legacy-local.mjs --capabilities`. Use the pinned local Playwright Chromium, never a hosted renderer or CI fallback. A private settings JSON file outside the checkout, or ignored by Git, has the same format as the V4 operator: `{ "sourceRevision": "<deployed-sha>", "environment": { "DATABASE_URL": "...", "STORAGE_PROVIDER_MODE": "neon", "NEON_STORAGE_BUCKET": "zyx-production", "AWS_ENDPOINT_URL_S3": "...", "AWS_REGION": "ap-southeast-1", "AWS_ACCESS_KEY_ID": "...", "AWS_SECRET_ACCESS_KEY": "...", "ZYX_ENVIRONMENT": "production", "ZYX_MCP_ENVIRONMENT": "production", "NODE_ENV": "production", "NEXT_PUBLIC_APP_URL": "https://www.zyxacademy.com", "BETTER_AUTH_URL": "https://www.zyxacademy.com", "AUTHORING_VERIFICATION_BROWSER_PROVIDER": "local_playwright" } }`. The production target guard validates the exact database and storage endpoint. Supply any other required server settings there as needed. Never paste real settings into a bundle, log or MCP response.

Create an input JSON file at an absolute path, with no secrets:

```json
{
  "privateFile": "/absolute/private/settings.json",
  "sourceRevision": "<40 lowercase hexadecimal characters>",
  "importId": "impor-product-<32 lowercase hexadecimal characters>",
  "runId": "mcp-run-<original staging UUID>",
  "expectedChecksum": "<64 lowercase hexadecimal characters>",
  "actorId": "<authorized admin ID>"
}
```

Run `node scripts/authoring/run-product-legacy-local.mjs --input /absolute/path/input.json`. Input is limited to 16 KiB and private settings to 128 KiB. Discovery returns `zyx-product-legacy-local-capabilities.v1`. The exact input and result JSON schemas are also available as `productBundle.legacyLocalOperator` from `workflow.get_contract`. Successful output contains `zyx-product-legacy-local-result.v1`, `status: "ready"`, the exact identity, browser version and revision, print profile, page count, PDF checksum, output directory and inventory of checksummed PDF, PNG and page text JSON files. Output may include JSON progress lines. A failed evidence attempt emits a `status: "failed"` result, followed by sanitized error JSON on stderr and a nonzero exit. Other errors emit sanitized stderr JSON and exit nonzero.

Each linked Diktat and each Article without a linked Diktat is an export target. Run once for each. If there is more than one target, provide `"diktatId": "<exact product ID>"` or `"articleId": "<exact product ID>"`; the fields are mutually exclusive. Omit both only for one eligible target. Each Diktat must link to its own Article revision. An Article-only export prints its ordered authored content and stores evidence under the Article ID. Its Article generation hash is also stored as self-lineage in the required legacy `diktatHash` column; no Diktat entity is created. The existing gate checks the actual Article version and hash. Formative answers remain protected. Safe inline links print their label and destination without fetching remote resources; unsupported reference-link syntax and unsafe protocols fail the export. Unsupported media, missing visual assets, invalid math, overflow or page-budget violations fail the attempt rather than omit content. Correct the source and restage if needed.

The process uses the existing compiler, print inspection and 1 to 4 page text inspection, verifies storage readback before marking evidence ready, then reads the stored PDF again and checksums the local files. It blocks external browser requests, limits the PDF and HTML sizes, runs one local process at a time and terminates its process group after 180 seconds. Artifacts are private local files under `artifacts/legacy-local-evidence/`. Inspect every page PNG and PDF for legibility, formulas, missing content and clipping before review. PDF readiness does not replace explicit semantic review by the authorized reviewer, which may be performed by an agent through the scoped MCP tools, or publication checks.

If the source, actor, staging audit or revision changes, obtain fresh context and make a new exact-revision decision. If the operator reports a lock, wait for the running process; only after verifying it exited, remove the indicated `zyx-product-local-<uid>.lock` directory in the system temporary directory. On timeout or interrupted export, check current evidence and readback before retrying. A pending or failed attempt is not ready. If the pinned browser is missing or mismatched, install the version reported by capabilities in the authorized local environment. On content or page-budget failure, correct and restage content, then use its new checksum and staging run. Never substitute a manually uploaded PDF, local assertion or V4 receipt for the required evidence.

## Request recovery

The request outcome GET may add `supersededByAttemptId` to an accepted outcome. This is a live attestation under the import lock that matching current-lineage evidence replaced the original attempt. The original acceptance audit stays immutable. The client adopts that exact replacement after a fresh detail read; it never treats an unrelated older ready PDF as acceptance. Once reconciled, status follows server evidence without a separate local pending mask.

A UUID saved before registration can remain unknown. If the bundle revision changes, the client can settle that original UUID and revision through POST. Registration either replays its terminal outcome or durably rejects the stale revision before any rendering. It does not submit a new render against the current revision. A request scope conflict offers the original account or an explicit stop of local tracking after refreshing current server readiness. That action removes only the browser pointer, leaving server request records and publication gates intact.

## Read models

Admin and student previews use the same semantic section renderer. The admin review surface shows section decisions and PDF readiness below the full-width article. A legacy PDF request reserves a checksum-bound pending evidence ID and audit record under the import lock before enqueue. The response includes `attemptId` and `duplicate`; concurrent requests for the same active attempt reuse the ID without sending another event. The event uses that ID for provider deduplication and the worker claims the same evidence. Pending evidence blocks older artifacts in status, review and publication, including across tabs and before a worker starts. Queue rejection marks only its own pending attempt failed. A transient worker retry keeps the same attempt and deadline. After 15 minutes from acceptance, status reports `failed` with `RENDER_TIMEOUT`, even if no worker wrote anything; an explicit retry reserves a new ID. The stored pending row continues to block publication until replaced, and an expired or superseded worker cannot commit. A pending attempt for an older checksum is reported as stale for the new revision and does not prevent a new request. The status refresh preserves review and content drafts for the unchanged revision; a revision change requires explicit reconciliation. A failed status refresh is not an active request: the reviewer can retry, or explicitly confirm leaving and discarding unsaved work. An interrupted POST requires a correlated outcome lookup; a terminal outcome then triggers draft-preserving status reconciliation before render or publication actions can resume. An unresolved outcome or failed reconciliation shows an unknown status, hides last-known ready links and offers a status retry. The history guard retains its origin during URL-tab replacements and advances it for inline item pushes, without bypassing Next URL-hook synchronization. It tracks entry positions before drafts become dirty. If an incoming position cannot be identified, it restores the origin by pushing its saved URL and state, discards unknown forward entries, and offers the intended destination after confirmation; it never probes an unknown document. Once current-lineage evidence exists for the current renderer print profile, selection uses that profile for status, review and publication, including pending or failed retries. Older-profile imports retain their fallback until then. V4 remains bound to its receipt. Internal Idea and provenance identifiers remain in the data model but are omitted from the reading surface and student view.

When `FEATURE_STRUCTURED_ARTICLE_READER_V1=1`, new Product Bundle submission must use V3 or later. An explicit V2 restage remains available only for the exact existing V2 draft and checksum in a verified matching run scope. The student material reader always prefers published canonical Article rows. Disabling the flag restores V2 submission without deleting V3 data or hiding published products.

PDF page images can be reused in `contentMarkdown` through the absolute `imageUrl` from a completed `source.read_file` or `source.get_read_job` response after requesting `representation: "image"` or `"both"`, followed by its human-readable `citation.label`. Preserve the source title, PDF page position, and document checksum in provenance. Never invent bibliographic details. Page renders are not isolated figures or typed interactive visuals and do not satisfy a typed-visual requirement.

Publication on both Admin and MCP requires the displayed 64-character checksum and an explicit whole-bundle approval by the publishing admin for that revision. Pedagogic approval alone cannot create or replace it. Readiness uses the same publisher, current dependency and V4 receipt checks on both surfaces. Restaging compares parsed Article and Diktat content before retaining PDF evidence, independently of the declared generation hash. Section decisions are read under the import lock before preservation.

Readiness and publication select the same PDF evidence row for the current Article and Diktat lineage. V4 additionally requires the current plan, attempt, signed receipt, print profile, page count and exact receipt artifact key; attachment must succeed before verification completes. A canonical Diktat version with a different existing file key is a version conflict and requires a new reviewed version. Legacy Article-owned PDF fallback follows the same selection policy in both gates.

MCP restaging checks the existing target artifact before processing replacement bytes, for every supported profile. Its exact checksum, course and chapter must match the active run, and it must contain learning products only. A historical assessment draft cannot be replaced through the learning-product tools, even with a learning-only replacement. The staging transaction still compares the caller's checksum before any review is cleared.

Refreshing PDF readiness preserves unsaved Admin rubric entries and decision notes when checksum, content fingerprint and policy are unchanged. If those identities change, the old draft remains visible and publication is blocked; opening the new revision requires explicit confirmation before discarding that draft.

Scoped lifecycle and verification tools require the actor and session bootstrap to be bound to the run at creation. A separate fresh bootstrap cannot upgrade an unbound legacy run. Restart through `workflow.start` with the same scope and source, then adopt an existing Product draft into that run when required by its staging identity before repeating verification and review.

Admin content-editor cancellation restores the server content without clearing review entries. Saving content applies the same revision-change confirmation as PDF refresh. PDF rendering and bundle review remain disabled while the content editor is open. Rubric and decision-note controls are disabled during submission. Closing mobile notes hides the field while preserving its text.

Local Product verifier launchers share one machine lock across imports, checkouts and legacy/V4 profiles, including capability discovery. The lock is acquired before bundling; each launch uses a private temporary module and cleans it up on exit. If a process is forcibly killed, first verify that no operator remains, then remove the per-user `zyx-product-local-<uid>.lock` directory under the operating system temporary directory before retrying. Per-import locks still protect the exact V4 attempt.

Structured section notes block bundle decisions, navigation, content edits and PDF requests while dirty or saving. Reviewers must save the section or explicitly discard its note changes; the section input is locked while saving. Non-Article legacy learning bundles expose approve and reject decisions, not the unsupported pedagogic request-changes action.

Admin review workspaces guard same-origin links and browser Back and Forward, including query-driven views, while review or content changes are unsaved, and warn on reload or tab close. Pending requests and their context refresh must finish before leaving. Changed Idea content requires confirmation when it invalidates existing reviewers’ decisions; unchanged content saves do not restage.

The optional Admin PDF route binds each action to one Diktat and a client-generated UUID. `POST /api/admin/bundles/product/{importId}/pdf` requires JSON `{ "productId": string, "expectedRevision": string, "requestId": UUID }`. The checksum is the exact 64-character lowercase revision. The authenticated admin is part of the request scope. The server registers that identity before loading the staged ZIP, and records acceptance with the pending evidence under the import lock before sending the worker event. Accepted POST responses use HTTP 202 and include `{ "requestId", "outcome": "accepted", "attemptId", "duplicate" }`, plus the target, revision and pending status. The accepted attempt may be shared with an already pending attempt for the same target and revision. Its original event retains its original actor.

After an ambiguous transport error, query `GET /api/admin/bundles/product/{importId}/pdf?outcome=1&requestId={uuid}&productId={productId}&expectedRevision={checksum}` with the same authenticated actor. HTTP 200 returns `{ "requestId", "outcome": "unknown" | "processing" | "accepted" | "rejected", "attemptId"?, "duplicate"?, "error"? }`. `unknown` means the request has not yet registered, and a delayed POST may still arrive. `processing` means registered without a final outcome. `accepted` names the exact attempt, while `rejected` is terminal for that request and has a safe error code. Reusing a UUID with another actor, import, product or revision returns `PRODUCT_DIKTAT_REQUEST_CONFLICT` (409). Explicit rejections include `outcome: "rejected"`; an invalid body or authorization failure is not a registered outcome. An unexpected service failure does not establish rejection. Retry an ambiguous POST with the same UUID; use a new UUID only after a terminal rejection or an accepted attempt's terminal failure. The optional Admin review persists unresolved request scope in URL parameters across reloads, hides older PDF links and blocks publication and new requests until the correlated outcome and a draft-preserving detail refresh are reconciled. Its status check queries the outcome, and its retry reuses the UUID for the original revision. A rejected request retains a retryable error after the refresh. An unresolved response permits confirmed navigation away, while a request or refresh actually in flight blocks navigation.

Registration has a fixed 15-minute processing deadline. Lookup or a later reservation records a terminal `PRODUCT_DIKTAT_REQUEST_TIMEOUT` after that deadline, and a late reservation cannot accept the expired request. While an unexpired registration is unresolved, shared readiness reports the blocking issue `PDF_REQUEST_PROCESSING`, the matching PDF status is pending without fabricated evidence, and publication rechecks the block under the import lock. The accepted attempt retains its separate fixed 15-minute worker deadline, replay, supersession and evidence checks. If enqueue fails after reservation, HTTP 503 includes `outcome: "accepted"`, the request and attempt IDs, and `PRODUCT_DIKTAT_PDF_QUEUE_UNAVAILABLE`; the server records failed evidence for that attempt when possible. Inspect the exact attempt and current evidence before starting a new request. Neither an absent registration nor a global ready or missing status establishes a request outcome.

The detail response supplies `pdfStatuses`, each with `productId`, `revision`, `status`, and selected evidence metadata. `pdfStatus` is a convenience only for a single Diktat; multiple targets return `select_product`, and an Article without a Diktat returns `source_missing`. PDF preview GET uses `productId` and `expectedRevision` with optional `download=1`. The Admin selects the active Diktat or the single Diktat linked to the active Article; multiple matches require selecting a Diktat. Status and preview share the publication lineage selector, including the legacy Article-owned fallback. A stale revision or evidence is rejected, including a check after downloading and before serving bytes. Scoped MCP review and publication and the private legacy local PDF operator remain supported without a mandatory Admin web step. V4 continues to require its separate trusted verification receipt.

Run adoption locks the import row before reading its staging audit. It rechecks draft status, checksum, object identity, course, version and validation report under that lock. A concurrent restage or adoption cannot overwrite the newer report or clear its reviews.

All Product staging, replacement and run-adoption audits receive a strictly increasing timestamp under the import or bundle-creation lock. Equal or skewed process clocks cannot reorder the current staging identity read by MCP and local operators.

Idempotent Product staging retries lock and reread the import before returning success. The requested checksum, draft identity, status, object key, course and profile must still match; item counts come from that locked snapshot. An intervening replacement or discard returns a stale-context conflict instead of success for an older revision.

Flat V2 embedded payloads use one public Markdown projection for Article PDF, canonical publication and new Article index jobs. It keeps the authored prompt, worked reasoning, visible options and units, while omitting answer keys, correctness and feedback. Private payloads remain in the restricted authoring artifact; flat legacy questions have no interactive evaluation endpoint. Unknown envelopes fail closed. Historical flat canonical text that still contains a private formative envelope, including nested JSON encoding or joined blocks, is withheld from both the student text lookup and Zyra retrieval or conversation-source hydration until repaired through the normal versioned authoring workflow. Existing external index entries are not rewritten by a local code change; inspect and reindex affected historical records through authorized maintenance. Withdrawal queues vector deletion from entity identity alone and does not require an old block to satisfy the newer public projection.

Use one authoring envelope per flat block. Raw JSON object fragments mixed into prose fail closed regardless of their field names or formative wrapper; readiness reports the block before publication. Ordinary prose such as `Kolom "content": isi pesan` remains valid. Intentionally public JSON examples belong inside inline or fenced code and remain literal public content; mathematical segments are not parsed as authoring objects. Idea, source-chunk and Product publication jobs retain the legacy course foreign key for queue ownership and dispatch, while their server-resolved `canonicalCourseId` supplies vector metadata. Chapter metadata uses the resolved canonical chapter. Article indexing and hydration strip only the managed visual-registry comment before computing retrieval text and its hash. Every canonical entity uses the same boundary-whitespace normalization for indexing and hydration hashes. Stored source content is not rewritten. Old already-indexed scope metadata is not rewritten by these local changes; inspect and replay or reindex it only against an authorized target.

The public projection is checked again after worked-example fields and all ordered V2 blocks are assembled. Readiness, canonical publication, indexing and Article-owned PDF compilation use that final projection, so fragments cannot evade validation by being split across blocks.

An unlinked Article PDF target requires self-lineage, including `diktatHash` equal to the current Article generation hash. Removing, adding or changing linked Diktat identities invalidates Article-owned PDF evidence. Old Diktat fallback rows cannot mask a pending or failed Article-only retry.

Article print preserves literal media syntax inside code while rejecting actual unsupported media. Its HTML includes semantic MathML and the authored TeX annotation alongside the visual formula. Extracted PDF text is a content-presence check, not mathematical verification: fractions, powers and layout may flatten. The reviewing agent must inspect every exported page image against the authored formula before recording its review; no Admin website visit is required.
