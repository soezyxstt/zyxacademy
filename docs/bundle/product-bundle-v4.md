# Product Bundle V4

Status: `ACTIVE`, source contract. Updated: 2026-11-26.

New learning Product authoring uses `product-bundle.v4`, `article.v4` and `diktat.v4` by default. Existing V3 bundles keep their version during legacy revisions unless a reviewed V4 conversion is requested. V2/V3 retain their readers and strict contracts. There is no additional feature flag or database migration. This document describes the local implementation, not deployment, installation on every host, or permission to publish a particular bundle.

## Machine-readable schema delivery

The [draft agent workflow update](authoring-agent-workflow.md) adds `productDraftInput` and `authoring.create_product_draft` for typed Article, Diktat and flashcard content, or one standalone V5 collection. The server builds the canonical archive from authored content and current source/Idea references. Its scope and limits are in `productBundle.initialDraft`; archive submission remains available. Canonical admission and each profile's release gates apply to both paths.

V4 separates content verification from final print artifacts. `authoring.verify_product_bundle` and `authoring.get_verification` accept `purpose: "logic"` by default or explicit `purpose: "pdf"`. Logic checks structure, references, notation, schemas and supported models without browser, PNG or PDF generation. PDF purpose produces final Diktat artifacts only when requested and reuses unchanged authenticated targets with matching runtime. Review binds the current logic receipt. Publication additionally requires exact canonical PDF bytes and current lineage for every included Diktat. Screenshots, page captures and visual inspection are optional and cannot block V4 publication. Legacy V2/V3 keep their existing policy.

`workflow.get_contract` exposes primary `productBundle.schemaDocuments` and retains `productBundle.pilot.schemaDocuments` as a compatibility alias, with exact same-origin GET paths, SHA-256 checksums and byte lengths. `/api/authoring/contracts/product-v4` lists those documents. Each `?schema=<name>` returns the full JSON Schema generated from the running Zod validator, including Product envelopes, dependencies, ordered parts, Diktat units, visual controls and bindings, review context and PDF evidence. The public endpoint contains type definitions only; it does not return any run or course data and requires no credential.

Use the checksum-pinned path returned by MCP and verify the response bytes. A stale pin returns HTTP 409; refresh the playbook and contract before continuing. `product` is the shared structural schema, so apply the explicit V4 `semanticRules` as well. JSON Schema cannot encode every cross-reference, lineage, security, model or readiness refinement. Complete validation still uses `authoring.validate_product_bundle`; validation success alone does not establish visual quality or publication readiness.

## Article representation

The Product envelope, sections, Idea links, source references and locked dependencies remain authoritative. A V4 Article has nonempty `sections`, empty top-level `blocks`, and 1 to 100 ordered `parts` per block. Stable IDs identify learning elements. IDs for parts, worked steps and relations must be unique across the Article.

| Kind | Required representation |
| --- | --- |
| `markdown` | `id`, `kind`, `markdown` |
| `math_unit` | `id`, `kind`, `meaningMarkdown`, exactly one of `latex` or nonempty `relations` |
| `visual_ref` | `id`, `kind`, `visualId`; optional `focusRefs` to Article elements |
| `worked_example` | `id`, `kind`, `title`, `problemMarkdown`, nonempty `steps`, `verificationMarkdown` |

A math unit may declare `conditionsMarkdown`, local `symbolDefinitions`, local `symbolRefs`, and layout `statement`, `derivation`, `cases` or `comparison`. Each relation has `id`, `latex`, `meaningMarkdown` and optional conditions. Cases require `conditionLatex` per relation. Symbols have `id`, `latex`, `meaningMarkdown` and optional conditions. Symbol references resolve within that math unit, not a global symbol registry.

Each worked step requires `id`, `operationMarkdown`, `reasonMarkdown`, `sourceElementRefs` and ordered leaf parts, plus optional conditions. Step references must resolve to previously available elements. Forward or missing references fail validation. Visual references resolve to the Article registry; their focus references must resolve to Article elements.

`parts` determines reading order. `materializeArticleParts` derives the compatibility Markdown, placing meanings, conditions and symbol definitions next to their formulas, and leaving visual markers in their authored positions. The validator derives referenced visual IDs before generation hashing. An omitted projection is filled; a differing supplied projection is rejected. Compiler, persisted metadata, reader and search carry the same element identities. Invalid V4 metadata fails closed instead of falling back to a legacy layout.

## Mathematical and scientific rendering

KaTeX with mhchem typesets marked mathematical prose, chemistry and units. Generated values use coefficient-times-power notation where appropriate. Axis scale exponents are displayed separately from quantity labels; physical units are upright and separated from symbols. Literal code and escaped currency remain literal. Arbitrary unmarked prose is not automatically rewritten as mathematics.

Most visual families are validated data rendered by application code. `interactive_document` is a separate reviewed executable artifact boundary: Article metadata stays inert, while the self-contained HTML and reviewed default-state PNG are packaged as private, checksum-bound assets. Supported data families include Learning Canvas, analytic epsilon-delta graphs, `geometry_2d`, `source_figure`, and `interactive_scene`. The V4 epsilon-delta board uses pinned JSXGraph; analytic delta derivation and numerical resolution checks remain independent of that library. Geometry uses validated references and equal physical axis scale. Unsupported or unrepresentable states fail or expose the accessible fallback.

Untuk `interactive_document`, Article dan Markdown menyimpan metadata saja. HTML mandiri yang ditinjau dapat memakai SVG, Canvas atau 3D secara offline. Untuk Product V4, gunakan `visual_ref`, sertakan `visuals/<documentSha256>.html` dan `visuals/<printSha256>.png`, lalu catat `{ "path", "sha256", "bytes" }` untuk setiap aset unik di `manifest.visualAssets`. Admission ZIP asinkron memeriksa referensi, hash dan panjang byte, menolak aset hilang atau tanpa referensi, serta mendekode PNG sepenuhnya sebelum staging. PNG harus statis, berukuran paling besar 4096 piksel per sisi dan 16 juta piksel, dengan dekompresi dibatasi oleh ukuran gambar. Validasi memeriksa CRC setiap chunk dan berjalan pada satu Node worker per proses, dengan antrean terbatas dan timeout. Setelah admission penuh dan pembacaan ulang aset, server menyimpan receipt privat berversi untuk hash dan panjang PNG. Delivery tetap memeriksa otorisasi field, manifest, panjang dan hash byte, lalu memerlukan receipt tersebut tanpa mendekode ulang PNG. Worker Diktat dan verifikasi V4 juga memerlukan receipt yang sama sebelum memakai aset; kegagalan admission tidak mengubah bukti PDF yang sudah ada. Data lama tanpa receipt gagal tertutup dan harus melalui admission penuh serta staging ulang. Penggantian draft dibatalkan sebelum penulisan jika artefak lama tidak dapat divalidasi untuk perbandingan review. Batas format adalah delapan spec, 6 MiB per HTML, 2 MiB per PNG dan 16 MiB total aset unik. Batas ini tidak membuktikan kapasitas transport MCP atau provider. Metadata tidak memuat source, base64, URL atau storage key. PNG keadaan awal menjadi aset cetak Diktat yang terikat checksum. Reviewer memeriksa isi, logika, hak penggunaan dan kesesuaian deklarasi aset; inspeksi tampilan opsional, bukan syarat publikasi V4.

Pada soal, `visualAssets` dikirim terpisah ke validasi dan submit sebagai `{ path, sha256, bytes, base64 }`; byte harus sesuai dengan metadata. Update visual baru atau berubah juga memerlukan byte tersebut. Update yang mempertahankan spec visual terikat dapat memakai ulang aset asli yang diverifikasi server tanpa mengirim ulang byte. Aset prompt atau opsi tidak boleh berbagi hash dengan pembahasan atau jawaban tersembunyi. Penggunaan visual selalu tersedia dengan aktivasi eksplisit dan pemuatan saat diperlukan. Aset privat diotorisasi berdasarkan versi, field dan aturan rilis konten, bukan hash saja. Satu GET iframe mengembalikan HTML dengan bootstrap kesiapan yang disisipkan server; sandbox membatasi dokumen dari host DOM. Bila belum siap setelah 15 detik, pengguna dapat mencoba lagi. Hash source mencakup byte asli tanpa bootstrap; fingerprint runtime mencakup implementasi bootstrap. Receipt verifikasi tetap terikat pada konten dan runtime.

Bacaan Article, percobaan Kuis, dan Tryout aktif di Expo memakai URL aset dan cakupan otorisasi yang sama dengan web. Pembaca Article memberi tombol pada bagian atau blok yang dirujuk, opsi cek, dan pembahasan setelah memperoleh grant. Percobaan Kuis memakai snapshot milik peserta, termasuk pembahasan yang telah dirilis. Tryout memakai soal dan opsi dari sesi ujian yang masih dibuka. Peserta bisa memilih visual interaktif atau PNG yang telah ditinjau. Expo memverifikasi panjang dan SHA-256 dari respons sebelum menampilkan aset. HTML hanya dimuat saat peserta membukanya, di dalam iframe lokal dengan sandbox dan tanpa bridge ke aplikasi. Bacaan offline mempertahankan fallback teks. Tampilan web saat SSR tetap memakai fallback sampai peserta mengaktifkan visual. Aksi baca ini tetap memakai sesi peserta dan izin yang sama, tanpa perubahan alat MCP, scope, consent, discovery, playbook, skill, prompt host, atau binding lingkungan. Gambar raster Markdown dari host HTTPS publik di Expo memakai pemuatan terpisah tanpa cookie, token atau referrer peserta. Pemuatan membatasi URL, redirect, jumlah permintaan, waktu, byte, dan dimensi header. Tautan bertanda tangan dan respons yang tidak memenuhi batas tetap menampilkan teks cadangan. Aset penyimpanan privat tetap memakai sesi peserta.

Dokumen menerima pesan hanya dari `event.source === parent`: `{ type: "zyx:preferences", theme: "light" | "dark", reducedMotion: boolean, active: boolean }` dan `{ type: "zyx:visibility", active: false }`. Hentikan animasi saat tidak aktif atau reduced motion, serta bersihkan timer dan observer pada `pagehide`. Sesudah layout berubah, kirim `parent.postMessage({ type: "zyx:resize", height }, "*")`; tinggi awal metadata dibatasi 240 sampai 1200 CSS px. Host menerima tinggi runtime 240 sampai 2400 CSS px, maksimal sekali per 100 ms, dan menerapkan tinggi valid terakhir setelah interval tersebut. Terapkan palet semantik Zyx, kontrol 14 px, teks terbaca, fokus keyboard, reset dan pemulihan nilai invalid. Periksa pula lebar opsi kuis sebenarnya. Tidak ada protokol akses istimewa ke host.

Untuk Product V4, verifikasi logika memeriksa struktur dan rujukan field formative serta model yang didukung. Reviewer tetap menilai jawaban, penalaran dan provenance. Receipt logika tidak mengklaim telah membuka browser, menguji keyboard, menjalankan HTML atau mengamati semua state. Pemeriksaan runtime opsional tetap dapat mencatat temuan nyata; screenshot dan inspeksi visual tidak menjadi gate publikasi V4. Admission aset, otorisasi field, batas reveal dan hak penggunaan tetap berlaku.

`interactive_scene` describes bounded 2D line, circle, rectangle, polygon, typed path and text primitives, parameters, numeric expressions, optional shape actions and a shared time parameter. Paths start with M and contain at most 32 M, L, Q, C or Z commands. The normalized JSON scene is limited to 131072 UTF-8 bytes, and an embedded Markdown fence is separately limited to 131072 UTF-16 code units. New Product Bundles require V4 for this family. `workflow.get_contract` returns field guidance, examples and a checksum-pinned visual schema generated from the validator. Put the spec in `article.visuals` and use an ordered `visual_ref`. Existing self-contained HTML may inform the model but must be translated to typed data; raw HTML, JavaScript and SVG markup are not import formats. The application produces SVG geometry, and Diktat renders the initial parameter state with the usual caption and snapshot pin. Three is installed but this contract does not provide a 3D renderer. Authors use `visual-teknik` to guide scientific and FBD decisions and verify assumptions, units, equations and states; schema validity does not prove the model.

Source figures refer to a stored asset ID, material ID and source checksum. Extraction binds the original PDF, page, normalized crop, SourcePack document and source visual. Preview and print variants carry checksums and transformation metadata. The stored manifest becomes usable only after both variants are written and checked. Learner delivery resolves through course access checks and a same-origin image route. Unknown rights prevent publication use. Delivery URLs are temporary and excluded from durable fingerprints.

## Authored Diktat and static export

A V4 bundle can contain any nonempty selection of Article, Diktat, flashcard set, and flashcard products. Each product keeps its own published Ideas and source references. An Article can publish without a Diktat. A standalone flashcard omits `setId` and is placed in the default collection for its course and chapter during publication. A standalone flashcard set uses `cards: []`. Explicit flashcard membership must resolve within the bundle.

A Diktat has 1 to 100 units. Each unit requires `id`, nonempty `ideaIds`, and ordered `parts`. Unit and part IDs, including nested steps and relations, are unique within the Diktat. For a standalone Diktat, omit all three Article lineage fields and unit `sourceElementRefs`. Unit Ideas cover the Diktat's own Idea links, worked steps resolve within its own ordered parts, and printable visuals resolve in its own optional registry. Interactive documents use their admitted static print asset.

For an explicitly derived Diktat, include its exact source Article, all three lineage fields (`sourceArticleId`, `sourceArticleVersion`, `sourceArticleHash`), and the locked Product dependency. Units cite Article elements through `sourceElementRefs`, cover its Ideas and preserve essential formulas and conditions. The Diktat uses the Article visual registry.

Diktat parts reuse Article Markdown, math units and worked examples. A top-level `visual_ref` adds `staticMarkdown` as an accessible caption, not as a replacement for the graphic. The server derives a `staticSnapshot` containing renderer version, visual hash and default-state hash when absent from a draft; a supplied stale pin is rejected. Static export renders actual validated plots, analytic epsilon/delta bands, diagrams, vectors, tables, chemistry, geometry and initial-state interactive scenes. Interactive documents use the pinned reviewed PNG. Source figures require trusted checksum-verified PNG or JPEG bytes supplied by the server. Missing assets, invalid math or unsupported export states fail closed.

`contentMarkdown` remains the derived textual projection. Final PDF compilation resolves graphical exports and validates local references or declared lineage. Standalone Diktat evidence records its own revision in the legacy Article version/hash columns. The print profile remains A4, 10.5 pt body, 1 to 4 pages without automatic shrinking, with the shared Diktat presentation, watermark, footer and page numbers. Rendering checks fonts, assets, math and printable bounds; invalid or oversized output fails the PDF artifact request. The PDF itself is read back and hashed against its exact canonical identity. Page screenshots and human visual inspection are not required. PDF readiness does not establish tagged-PDF accessibility or educational effectiveness.

## Trusted verification and explicit review

V4 verification and publication reject obvious unmarked mathematical notation in learner prose, including absolute-value expressions, equations, caret exponents, scientific e notation and Unicode mathematical glyphs. Authors must supply explicit math delimiters. Numeric e notation is rejected even inside math delimiters or authored LaTeX; use explicit multiplication by a power of ten. Valid unit macros that normalize scientific input remain supported. Correctly formatted math, code, currency, function-expression models and typed numeric table data are preserved; the guard does not rewrite prose or replace semantic review.

Structural validity permits staging. The server then derives a purpose-bound plan from the stored bundle and dependency closure. The default logic plan checks content without any rendering requirement. The separate PDF plan targets final Diktat artifacts. An agent cannot remove required checks or substitute a plan from the other purpose.

The current logic policy requires structural, reference and notation checks plus supported numerical/model checks for authored Article and Diktat content. It schedules no Article reader, visual-smoke, screenshot, text-zoom or PDF checks. Explicit PDF purpose creates one final PDF per applicable Diktat and no page-image requirement. Policy and purpose bind the plan hash, so older visual-policy receipts cannot be treated as current logic receipts. A supported model check or sampled value is not a general mathematical proof; authored semantic review remains required.

Both purposes bind exact content, import/run scope, live dependencies, policy and their applicable runtime. Logic has no browser-provider prerequisite. PDF additionally binds its renderer, print profile, assets and browser/runtime identity. The application persists observed results and issues an HMAC-authenticated receipt for that exact purpose and plan. PDF artifact bytes are read back and checked. Missing, failed, stale or contradictory evidence remains non-ready for its own purpose. Explicit retry keeps the same purpose and exact current identity; replacing a failed attempt retains snapshot and attempt compare-and-swap guards. Storage permission and transport failures are not treated as missing content. Logic readiness does not imply PDF readiness, and PDF success cannot approve the content.

The private local operator `node scripts/authoring/run-product-v4-local.mjs` is PDF-only. Its server-selected purpose is fixed; the input file does not take a purpose override. Discover pins with `--capabilities`, then use `--input <absolute-input-json-path>` with `privateFile`, `sourceRevision`, `importId`, `runId`, `expectedChecksum` and optional `retry`. The settings file stays outside the checkout or Git-ignored. The operator requires the exact supported target, clean deployed source and staging run. Default logic verification uses the browser-free server job instead.

For an unchanged Admin-staged draft, an authorized active admin can explicitly call `authoring.adopt_product_draft_run` with the verified course and chapter run, product bootstrap, checksum and observed `expectedStagingRunId`. This records the previous staging identity and new run in an audit, invalidates prior verification, PDF evidence and bundle review, and leaves the artifact unchanged. Fetch context again, run logic verification and semantic review for the adopted run, and request purpose `pdf` separately when final Diktat artifacts are needed. Stale scope or identity fails the transaction.

Local and hosted attempts bind to the latest staging audit and its run. Attempt attachment and PDF evidence persistence lock the import and compare that audit with the original import snapshot. Readiness rejects an attempt from an earlier staging identity, including an earlier identity for the same run and checksum. Existing verification references without a staging audit identity require a fresh trusted verification; prior signed receipts and PDF artifacts alone do not satisfy this gate. New attempts require a draft, so an already published import with an older reference cannot be reverified in place. Its read-only Admin PDF preview can use the matching published bundle record, published item inventory with the complete product hash, and exact canonical Diktat file identity, version, course, source hash and generation hash, together with matching ready PDF evidence. The original stored receipt must authenticate as server-observed with the configured signing authority, match the recorded plan and attempt, and identify that exact PDF artifact. The downloaded PDF size and checksum must match the signed artifact before any bytes are served. Missing or invalid proof makes the preview unavailable. This historical preview does not supply trusted readiness or draft publication evidence. Withdrawn, changed or unrecorded identities remain unavailable. This does not change the receipt signature, artifact readback, review or publication requirements.

For explicit PDF purpose, `local_playwright` runs pinned Chromium on an authorized operator's computer. Existing production target, database, storage and process guards apply before writes. Private settings load before application imports, and hosted fingerprint overrides remain rejected. The service creates and reads back real PDF bytes, signs the matching print results and persists current PDF evidence. Its result reports `purpose: "pdf"`, exact identity and verified artifacts. It neither creates the logic receipt nor approves semantic review. Hosted PDF requests follow the configured worker; local PDF requests do not enqueue a hosted browser job.

V4 approval requires the exact revision, quality-policy fingerprint, current logic plan/receipt, complete content rubric and an explicit current semantic decision for every Article section. Review checks source claims, reasoning, calculations, units, assumptions, domain bounds and answers without mandatory visual inspection. Article-free bundles use document anchors and no fabricated sections. Publication repeats these checks and requires current canonical PDFs for included Diktats, while claiming the unchanged import snapshot transactionally. Stale content, dependencies or evidence cannot authorize a newer revision.

An authorized agent can obtain the staged learning content, section hashes, criterion identifiers and receipt references with `authoring.get_product_review_context`, then record review with `authoring.review_product_bundle`. An admin with `authoring:publish` can explicitly call `authoring.publish_product_bundle` using the verified product bootstrap, course/chapter run and exact checksum. The publication service repeats its authorization, traceability, review, verification and PDF gates. The scoped tool excludes V2 assessment entities. V5 has its own item review contract. The V4 local verifier does not generate legacy V2/V3 PDF evidence.

Admin detail evaluates the full stored bundle, including its manifest, with current logic readiness. It presents PDF artifact readiness separately. The Publish gate requires valid content, current logic and semantic review, plus the applicable canonical Diktat PDFs. An unavailable browser or optional preview does not block Article-only V4 publication.

## Validation and operational boundaries

The manual `Operate V4 verification` GitHub Actions workflow uses the selected GitHub environment for `inspect`, `retry`, `evidence` and `cancel`. Its `verify` job uses Bun 1.3.14, matching the application and worker runtime build, and runs the helper with `--conditions=react-server` to resolve the existing server-only module markers. Staging runs require the `staging` branch; production runs require `main`. Before loading database or storage clients, `scripts/authoring/operate-v4-verification.ts` validates that environment's app origin, exact Neon PostgreSQL host and `neondb` database, `sslmode=verify-full`, private Neon storage endpoint, bucket and region against the approved worker target profiles. It reads only `DATABASE_URL` for the application database; legacy Turso settings cannot override it. Both `postgres:` and `postgresql:` schemes receive the same checks; the alias is normalized only for validation and the application receives the original setting.

The workflow uses the selected environment's `DATABASE_URL`, `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` secrets. `AWS_ENDPOINT_URL_S3`, `NEON_STORAGE_BUCKET` and `AWS_REGION` come from its variables or secrets and must match the approved target. Missing or redacted credentials and mixed targets fail before any client initializes. The storage adapter uses `STORAGE_PROVIDER_MODE=neon` and no public asset URL.

Supply the exact bundle checksum as `revision` for an existing draft and run. `inspect` without a revision lists V4 drafts; with a revision it reports the current check, failure code, retry time and current-attempt artifact counts. Optional Inngest diagnostics retain their existing sanitized queue and failed-step output when those provider records are available. `evidence` exports only a currently ready, signed attempt after artifact byte and checksum verification, with its current PDF evidence when required. The Actions artifact is retained for three days; [signed-in users with repository read access can download it](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts). It contains learning content and observed artifacts, without account or storage metadata. Review that audience before running `evidence`; uploading an artifact does not change repository visibility or create a private access boundary. A changed runtime or plan requires fresh trusted verification; this helper cannot override fingerprints, publish, approve or supply substitute evidence. The production-only local operator and the separate legacy `prepare-fixture` workflow jobs keep their existing boundaries. These maintenance changes add no MCP tool, scope, consent or publication path; deployed runtime and workflow access still require separate acceptance.

The test suite covers contracts, supported models, lineage, purpose isolation, HMAC receipts, artifact readback, dependencies, explicit review and PostgreSQL-compatible compare-and-swap checks. Optional browser/PDF inspection is separate evidence, never a hidden V4 publication requirement. Record actual command outcomes and any optional captures in the implementation report; synthetic checks do not establish teaching quality or deployed service health.

Server playbooks and plugin build/host checks have separate provenance. Updating repository guidance does not establish that every installed plugin, active OAuth connection or external executor is current. Fresh live bootstrap and scoped read-only tool calls are required for each host. No deployment or remote mutation is implied by local tests.

Implementation authorities: `lib/materials/article-parts.ts`, `diktat-v4.ts`, `diktat-static-visual.ts`, `diktat-print-readiness.ts`, `lib/bundle/product-validator.ts`, `product-diktat-pdf.ts`, `product-v4-verification.ts`, `product-v4-verification-service.ts`, `product-v4-review.ts`, and the [system design](../../plans/article-diktat-authoring-system-design.md). Operational acceptance and chapter rollout remain tracked separately from this active contract.

## Replacement and readiness

All Product profiles require `expectedPreviousChecksum` for replacement at the shared staging service. Replacement revalidates the stored artifact before uploading or changing the draft. A failed download, admission or identity check preserves the prior artifact and reviews, so a transient print-admission failure can be retried safely. MCP restaging carries the caller's `expectedRevision` unchanged; submission without it is create-only when the bundle ID differs in content. Readiness is scoped to the current publisher, including bundle and section decisions and live source dependencies. Publication holds share locks on referenced Ideas, sources, excerpts and external Product dependencies until commit. Import listing evaluates one artifact at a time to bound concurrent memory use.

V4 verification checks the actual staged chapter and original staging run before attaching an attempt. Missing read or stage scope returns an OAuth `insufficient_scope` challenge with the required scope. Local Playwright attempts require the local operator to execute them; polling does not start a hosted worker.

External Product dependencies must still be published under their transaction share locks. V4 readiness and publication apply the same stored-review validation against the current plan, signed receipt and section hashes. A new verified receipt requires a matching review.

Dependency lookup shares the canonical Product version-ID mapping with publication and runtime verification: version 1 uses the logical ID, later versions use `id:vN`. Live blueprint dependencies use their `approved` status; other Product dependencies require `published`. Retired entries fail verification.

MCP draft discard uses `authoring.discard_product_draft` with the verified product `runToken`, `bootstrapToken`, `importId` and caller-observed `expectedRevision`, plus `authoring:withdraw`. It rejects stale revisions, other chapters and assessment profiles. Admin item review and draft deletion also submit the displayed checksum. Shared content-addressed artifacts are retained until safe cleanup.

Readiness and publication select the same PDF evidence row for the current Diktat revision and any declared Article lineage. V4 additionally requires the current plan, attempt, signed receipt, print profile, page count and exact receipt artifact key; attachment must succeed before PDF-purpose verification completes. A canonical Diktat version with a different existing file key is a version conflict and requires a new reviewed version. Legacy Article-owned PDF fallback follows the same selection policy in both gates.

Local Product verifier launchers share one machine lock across imports, checkouts and legacy/V4 profiles, including capability discovery. The lock is acquired before bundling; each launch uses a private temporary module and cleans it up on exit. If a process is forcibly killed, first verify that no operator remains, then remove the per-user `zyx-product-local-<uid>.lock` directory under the operating system temporary directory before retrying. Per-import locks still protect the exact V4 attempt.

The Admin hides legacy PDF rendering for V4 and directs the reviewer to explicit final PDF generation. The Admin PDF POST route does not enqueue legacy rendering for V4. It returns `PRODUCT_V4_TRUSTED_VERIFICATION_REQUIRED`; recover through the V4 tool with purpose `pdf`. PDF GET requires the exact `productId` and `expectedRevision`, and serves only the evidence bound to the current PDF receipt, plan, profile and page count.

Run adoption locks the import row before reading its staging audit. It rechecks draft status, checksum, object identity, course, version and validation report under that lock. A concurrent restage or adoption cannot overwrite the newer report or clear its reviews.

All Product staging, replacement and run-adoption audits receive a strictly increasing timestamp under the import or bundle-creation lock. Equal or skewed process clocks cannot reorder the current staging identity read by MCP and local operators.

Idempotent staging retries return success only after locking and rereading the requested import identity and verifying its recorded ZIP against the checksum. A missing archive is restored at the recorded key and verified before success. A concurrent replacement or discard returns a stale-context conflict. The synthetic local fixture harness supplies an in-memory staging identity and exact PDF attachment selection. Its reports do not establish canonical database promotion or trusted deployed verification.

## Local draft preview and authored priorities

The typed draft input can preserve explicit `ideaLinks` weights/roles for exactly its `ideaIds`; versions/hashes remain server-bound. `productBundle.localPreview` advertises `bun run authoring:preview` for the same raw input, plus watch and structure-only modes. Preview uses shared learner/print components and exports screenshots, outline, diagnostics and Diktat pages. It never checks live sources or grants a receipt, review or publication readiness. Targeted Diktat-unit edits rebuild projections and invalidate affected evidence. See [the agent workflow](authoring-agent-workflow.md) for boundaries and repeatable synthetic measurements.
