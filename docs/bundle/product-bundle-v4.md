# Product Bundle V4

Status: `ACTIVE`, source contract. Updated: 2026-11-11.

New Article/Diktat authoring uses `product-bundle.v4`, `article.v4` and `diktat.v4` by default. Existing V3 bundles keep their version during legacy revisions unless a reviewed V4 conversion is requested. V2/V3 retain their readers and strict contracts. There is no additional feature flag or database migration. This document describes the local implementation, not deployment, installation on every host, or permission to publish a particular bundle.

## Machine-readable schema delivery

`workflow.get_contract` exposes primary `productBundle.schemaDocuments` and retains `productBundle.pilot.schemaDocuments` as a compatibility alias, with exact same-origin GET paths, SHA-256 checksums and byte lengths. `/api/authoring/contracts/product-v4` lists those documents. Each `?schema=<name>` returns the full JSON Schema generated from the running Zod validator, including Product envelopes, dependencies, ordered parts, Diktat units, visual controls and bindings, review context and PDF evidence. The public endpoint contains type definitions only; it does not return any run or course data and requires no credential.

Use the checksum-pinned path returned by MCP and verify the response bytes. A stale pin returns HTTP 409; refresh the playbook and contract before continuing. `product` is the shared structural schema, so apply the explicit V4 `semanticRules` as well. JSON Schema cannot encode every cross-reference, lineage, security, model or readiness refinement. Complete validation still uses `authoring.validate_product_bundle`; validation success alone does not establish visual quality or publication readiness.

## Article representation

The Product envelope, sections, Idea links, source references and locked dependencies remain authoritative. A V4 Article has nonempty `sections`, empty top-level `blocks`, and 1 to 100 ordered `parts` per block. Stable IDs identify learning elements. IDs for parts, worked steps and relations must be unique across the Article.

| Kind | Required representation |
| --- | --- |
| `markdown` | `id`, `kind`, `markdown` |
| `math_unit` | `id`, `kind`, `meaningMarkdown`, exactly one of `latex` or nonempty `relations` |
| `visual_ref` | `id`, `kind`, `visualId`; optional `focusRefs` to Article elements |
| `worked_example` | `id`, `kind`, `title`, `problemMarkdown`, nonempty `steps`, `verificationMarkdown` |

A math unit may declare `conditionsMarkdown`, local `symbolDefinitions`, local `symbolRefs`, and layout `statement`, `derivation`, `cases` or `comparison`. Each relation has `id`, `latex`, `meaningMarkdown` and optional conditions. Cases require `conditionLatex` per relation. Symbols have `id`, `latex`, `meaningMarkdown` and optional conditions. Symbol references resolve within that math unit, not a global symbol registry.

Each worked step requires `id`, `operationMarkdown`, `reasonMarkdown`, `sourceElementRefs` and ordered leaf parts, plus optional conditions. Step references must resolve to previously available elements. Forward or missing references fail validation. Visual references resolve to the Article registry; their focus references must resolve to Article elements.

`parts` determines reading order. `materializeArticleParts` derives the compatibility Markdown, placing meanings, conditions and symbol definitions next to their formulas, and leaving visual markers in their authored positions. The validator derives referenced visual IDs before generation hashing. An omitted projection is filled; a differing supplied projection is rejected. Compiler, persisted metadata, reader and search carry the same element identities. Invalid V4 metadata fails closed instead of falling back to a legacy layout.

## Mathematical and scientific rendering

KaTeX with mhchem typesets marked mathematical prose, chemistry and units. Generated values use coefficient-times-power notation where appropriate. Axis scale exponents are displayed separately from quantity labels; physical units are upright and separated from symbols. Literal code and escaped currency remain literal. Arbitrary unmarked prose is not automatically rewritten as mathematics.

Most visual families are validated data rendered by application code. `interactive_document` is a separate reviewed executable artifact boundary: Article metadata stays inert, while the self-contained HTML and reviewed default-state PNG are packaged as private, checksum-bound assets. Supported data families include Learning Canvas, analytic epsilon-delta graphs, `geometry_2d`, `source_figure`, and `interactive_scene`. The V4 epsilon-delta board uses pinned JSXGraph; analytic delta derivation and numerical resolution checks remain independent of that library. Geometry uses validated references and equal physical axis scale. Unsupported or unrepresentable states fail or expose the accessible fallback.

Untuk `interactive_document`, Article dan Markdown menyimpan metadata saja. HTML mandiri yang ditinjau dapat memakai SVG, Canvas atau 3D secara offline. Untuk Product V4, gunakan `visual_ref`, sertakan `visuals/<documentSha256>.html` dan `visuals/<printSha256>.png`, lalu catat `{ "path", "sha256", "bytes" }` untuk setiap aset unik di `manifest.visualAssets`. Admission ZIP asinkron memeriksa referensi, hash dan panjang byte, menolak aset hilang atau tanpa referensi, serta mendekode PNG sepenuhnya sebelum staging. PNG harus statis, berukuran paling besar 4096 piksel per sisi dan 16 juta piksel, dengan dekompresi dibatasi oleh ukuran gambar. Validasi memeriksa CRC setiap chunk dan berjalan pada satu Node worker per proses, dengan antrean terbatas dan timeout. Setelah admission penuh dan pembacaan ulang aset, server menyimpan receipt privat berversi untuk hash dan panjang PNG. Delivery tetap memeriksa otorisasi field, manifest, panjang dan hash byte, lalu memerlukan receipt tersebut tanpa mendekode ulang PNG. Worker Diktat dan verifikasi V4 juga memerlukan receipt yang sama sebelum memakai aset; kegagalan admission tidak mengubah bukti PDF yang sudah ada. Data lama tanpa receipt gagal tertutup dan harus melalui admission penuh serta staging ulang. Penggantian draft dibatalkan sebelum penulisan jika artefak lama tidak dapat divalidasi untuk perbandingan review. Batas format adalah delapan spec, 6 MiB per HTML, 2 MiB per PNG dan 16 MiB total aset unik. Batas ini tidak membuktikan kapasitas transport MCP atau provider. Metadata tidak memuat source, base64, URL atau storage key. PNG keadaan awal dipakai sebagai snapshot cetak Diktat; kesesuaian dengan keadaan awal tetap perlu ditinjau manusia.

Pada soal, `visualAssets` dikirim terpisah ke validasi dan submit sebagai `{ path, sha256, bytes, base64 }`; byte harus sesuai dengan metadata. Update visual baru atau berubah juga memerlukan byte tersebut. Update yang mempertahankan spec visual terikat dapat memakai ulang aset asli yang diverifikasi server tanpa mengirim ulang byte. Aset prompt atau opsi tidak boleh berbagi hash dengan pembahasan atau jawaban tersembunyi. Penggunaan visual selalu tersedia dengan aktivasi eksplisit dan pemuatan saat diperlukan. Aset privat diotorisasi berdasarkan versi, field dan aturan rilis konten, bukan hash saja. Satu GET iframe mengembalikan HTML dengan bootstrap kesiapan yang disisipkan server; sandbox membatasi dokumen dari host DOM. Bila belum siap setelah 15 detik, pengguna dapat mencoba lagi. Hash source mencakup byte asli tanpa bootstrap; fingerprint runtime mencakup implementasi bootstrap. Receipt verifikasi tetap terikat pada konten dan runtime.

Dokumen menerima pesan hanya dari `event.source === parent`: `{ type: "zyx:preferences", theme: "light" | "dark", reducedMotion: boolean, active: boolean }` dan `{ type: "zyx:visibility", active: false }`. Hentikan animasi saat tidak aktif atau reduced motion, serta bersihkan timer dan observer pada `pagehide`. Sesudah layout berubah, kirim `parent.postMessage({ type: "zyx:resize", height }, "*")`; tinggi awal metadata dibatasi 240 sampai 1200 CSS px. Host menerima tinggi runtime 240 sampai 2400 CSS px, maksimal sekali per 100 ms, dan menerapkan tinggi valid terakhir setelah interval tersebut. Terapkan palet semantik Zyx, kontrol 14 px, teks terbaca, fokus keyboard, reset dan pemulihan nilai invalid. Periksa pula lebar opsi kuis sebenarnya. Tidak ada protokol akses istimewa ke host.

Verifikasi field formative mencakup prompt, opsi, jawaban hasil reveal dan pembahasan pada kedua viewport. Runner mengikat field dan aset ke plan saat ini, memeriksa perubahan keyboard dan reset, serta memakai respons reveal berscope dan grant sintetis. Fixture admitted dengan runner sebenarnya lulus lokal; ini tidak membuktikan endpoint autentikasi atau penyimpanan nyata. Gate publikasi tetap membutuhkan receipt exact-revision dan review. Layanan MCP aktif, deployment, hak penggunaan dan kebenaran ilmiah memerlukan pemeriksaan terpisah. Output skill visual perlu diterjemahkan atau diadaptasi ke kontrak dan ditinjau oleh author; fixture authored generik bukan katalog model siap pakai.

`interactive_scene` describes bounded 2D line, circle, rectangle, polygon, typed path and text primitives, parameters, numeric expressions, optional shape actions and a shared time parameter. Paths start with M and contain at most 32 M, L, Q, C or Z commands. The normalized JSON scene is limited to 131072 UTF-8 bytes, and an embedded Markdown fence is separately limited to 131072 UTF-16 code units. New Product Bundles require V4 for this family. `workflow.get_contract` returns field guidance, examples and a checksum-pinned visual schema generated from the validator. Put the spec in `article.visuals` and use an ordered `visual_ref`. Existing self-contained HTML may inform the model but must be translated to typed data; raw HTML, JavaScript and SVG markup are not import formats. The application produces SVG geometry, and Diktat renders the initial parameter state with the usual caption and snapshot pin. Three is installed but this contract does not provide a 3D renderer. Authors use `visual-teknik` to guide scientific and FBD decisions and verify assumptions, units, equations and states; schema validity does not prove the model.

Source figures refer to a stored asset ID, material ID and source checksum. Extraction binds the original PDF, page, normalized crop, SourcePack document and source visual. Preview and print variants carry checksums and transformation metadata. The stored manifest becomes usable only after both variants are written and checked. Learner delivery resolves through course access checks and a same-origin image route. Unknown rights prevent publication use. Delivery URLs are temporary and excluded from durable fingerprints.

## Authored Diktat and static export

V4 requires its source Article in the same bundle, matching `sourceArticleId`, `sourceArticleVersion` and `sourceArticleHash`, plus its locked dependency. Publication requires the authored Diktat for that Article. The review path supports one Article and at most one Diktat per V4 bundle; a publication-ready bundle contains both.

A Diktat has 1 to 100 units. Each unit requires `id`, nonempty `sourceElementRefs`, nonempty `ideaIds`, and ordered `parts`. IDs include nested worked steps and relations. References resolve to source Article elements; aggregate Idea coverage matches the Article. Essential formulas and their conditions must survive compression. Worked steps cannot refer to unknown elements. These structural checks support, but do not prove, semantic equivalence.

Diktat parts reuse Article Markdown, math units and worked examples. A top-level `visual_ref` adds `staticMarkdown` as an accessible caption, not as a replacement for the graphic. The server derives a `staticSnapshot` containing renderer version, visual hash and default-state hash when absent from a draft; a supplied stale pin is rejected. Static export renders actual validated plots, analytic epsilon/delta bands, diagrams, vectors, tables, chemistry, geometry and initial-state interactive scenes. Interactive documents use the pinned reviewed PNG. Source figures require trusted checksum-verified PNG or JPEG bytes supplied by the server. Missing assets, invalid math or unsupported export states fail closed.

`contentMarkdown` remains the derived textual projection. PDF compilation resolves graphical exports separately and validates lineage again. The print profile remains A4, 10.5 pt body text, 1 to 4 pages, without automatic shrinking. V4 units use a 1 mm paragraph gap while retaining the body font size and line height. Browser readiness checks wait for fonts and assets, reject math errors, clipped visual labels, horizontal overflow and units taller than the printable page. Oversized content requires splitting or revising its scope. Every generated PDF page must be inspected and represented in the verification receipt. PDF text extraction, screenshots and fixed typography do not establish tagged-PDF accessibility or educational effectiveness.

## Trusted verification and explicit review

V4 verification and publication reject obvious unmarked mathematical notation in learner prose, including absolute-value expressions, equations, caret exponents, scientific e notation and Unicode mathematical glyphs. Authors must supply explicit math delimiters. Numeric e notation is rejected even inside math delimiters or authored LaTeX; use explicit multiplication by a power of ten. Valid unit macros that normalize scientific input remain supported. Correctly formatted math, code, currency, function-expression models and typed numeric table data are preserved; the guard does not rewrite prose or replace semantic review.

Structural validity allows a draft to be staged. It is not publication readiness. The server derives the complete requirement matrix from the stored bundle and dependency closure, including structure, model, web states at 380 by 844 and 1536 by 864, and printable pages. An agent cannot remove checks by submitting its own matrix or declaring a check not applicable.

Policy `product-v4-verification.v2` requires one structure check, Article reading-order/math and keyboard/text-zoom checks at both viewports, one model check per visual, and one combined `visual-smoke` per visual at each viewport. The smoke combines applicable default, fallback, interaction, reset, keyboard and boundary behavior in one observed check rather than repeating separate state captures. Diktat retains both print checks, including every PDF page at the fixed A4 profile. One Article with eight visuals and one Diktat therefore has 31 requirements. The policy revision changes the exact plan hash and invalidates earlier receipts; HMAC signatures, server-observed origin, scope and dependency bindings, artifact readback, stale-revision rejection, PDF evidence and explicit review remain required. This policy contract does not establish deployment or publication success.

The plan binds the configured browser provider and exact Chromium version, exact content, import and run scope, live Idea/source/product dependencies, renderer source and package versions, fonts, contract, playbook, assets, print profile and policy. Any applicable change invalidates the old plan. Application-owned execution persists actual artifacts before issuing an HMAC-authenticated receipt. Artifact bytes are read back and checked. Local or agent reports remain reported evidence and cannot satisfy trusted readiness. Missing, failed, untested, stale or contradictory evidence blocks readiness. A completed signed attempt with a missing or checksum-mismatched artifact is reported as failed and can be retried explicitly in the same staging identity and run, through the local operator or MCP. Confirmed absent manifest or state metadata also reports a failed, explicitly retryable attempt after bounded read retries. Malformed metadata is non-ready and explicitly replaceable; valid conflicting run or attempt identities remain errors. The replacement attempt still uses the snapshot and attempt compare-and-swap guards. Storage permission and transport errors remain errors, rather than evidence of damaged or absent content.

The private local operator launcher is `node scripts/authoring/run-product-v4-local.mjs`. Use `--capabilities` to discover the current reviewed browser pin, installed Playwright revision and runtime fingerprints from the exact checkout. Use `--input <absolute-input-json-path>` for execution. The input JSON contains `privateFile`, `sourceRevision`, `importId`, `runId`, `expectedChecksum`, and optional `retry`; `workflow.get_contract` describes their exact format. The private settings file must be outside the checkout or Git-ignored. The runner requires the clean deployed source revision and the run that last staged this exact draft. `authoring.get_product_review_context` exposes that staging run when available.

For an unchanged Admin-staged draft, an authorized active admin can explicitly call `authoring.adopt_product_draft_run` with the verified course and chapter run, product bootstrap, checksum and observed `expectedStagingRunId`. This records the previous staging identity and new run in an audit, invalidates prior verification, PDF evidence and bundle review, and leaves the artifact unchanged. Fetch the context again and use the adopted run for a fresh local verification and review. Stale scope or identity fails the transaction.

Local and hosted attempts bind to the latest staging audit and its run. Attempt attachment and PDF evidence persistence lock the import and compare that audit with the original import snapshot. Readiness rejects an attempt from an earlier staging identity, including an earlier identity for the same run and checksum. Existing verification references without a staging audit identity require a fresh trusted verification; prior signed receipts and PDF artifacts alone do not satisfy this gate. New attempts require a draft, so an already published import with an older reference cannot be reverified in place. Its read-only Admin PDF preview can use the matching published bundle record, published item inventory with the complete product hash, and exact canonical Diktat file identity, version, course, source hash and generation hash, together with matching ready PDF evidence. The original stored receipt must authenticate as server-observed with the configured signing authority, match the recorded plan and attempt, and identify that exact PDF artifact. The downloaded PDF size and checksum must match the signed artifact before any bytes are served. Missing or invalid proof makes the preview unavailable. This historical preview does not supply trusted readiness or draft publication evidence. Withdrawn, changed or unrecorded identities remain unavailable. This does not change the receipt signature, artifact readback, review or publication requirements.

The `local_playwright` provider runs pinned Chromium on the operator's computer, with no hosted browser or CI dependency. Production database, storage, origin and local-process guards run before an attempt is written. Private settings load before application imports; hosted runtime and embedded fingerprint overrides are rejected. The application service executes the real checks, reuses one browser, signs the observed results, reads back artifacts and persists PDF evidence. A local report uploaded by an agent still cannot substitute for that execution. Local verification requests do not enqueue a hosted browser job. The `zyx-product-v4-local-result.v1` result identifies the exact checksum, plan, attempt, receipt signature, output directory and checksum/size-verified artifact inventory. Errors use a sanitized code and recovery guidance. Inspect the exact artifacts before separate pedagogic approval and publication.

V4 approval requires the exact revision, quality-policy fingerprint, current verification plan and receipt signature, a complete criterion rubric, and an explicit current semantic decision for every section. Legacy whole-bundle approval cannot silently approve V4 sections. Publication repeats these checks and claims the unchanged import snapshot inside the transaction; stale content, evidence or concurrent replacement must not receive approval or publication from an earlier snapshot.

An authorized agent can obtain the staged learning content, section hashes, criterion identifiers and receipt references with `authoring.get_product_review_context`, then record review with `authoring.review_product_bundle`. An admin with `authoring:publish` can explicitly call `authoring.publish_product_bundle` using the verified product bootstrap, course/chapter run and exact checksum. The publication service repeats its authorization, traceability, review, verification and PDF gates. The scoped tool excludes V2 assessment entities. V5 has its own item review contract. The V4 local verifier does not generate legacy V2/V3 PDF evidence.

Admin detail evaluates the complete stored bundle, including its manifest, with the current trusted verification result. The quality status and review context reuse that result so the Publish button agrees with the publication gate. Missing or invalid verification, PDF evidence or review still blocks publication.

## Validation and operational boundaries

The test suite contains contract, model, lineage, HMAC/receipt, artifact-readback, dependency, explicit-review and local PostgreSQL-compatible compare-and-swap checks. Primary-agent browser and PDF inspection remains separate evidence. Static-family fixtures generate small compiled documents for numerical plots, derivations, tables, chemistry, diagrams, vectors, geometry and a real PDF-derived source figure. Exact current command outcomes and screenshot/PDF paths belong in the local verification report, not this contract.

Server playbooks and plugin build/host checks have separate provenance. Updating repository guidance does not establish that every installed plugin, active OAuth connection or external executor is current. Fresh live bootstrap and scoped read-only tool calls are required for each host. No deployment or remote mutation is implied by local tests.

Implementation authorities: `lib/materials/article-parts.ts`, `diktat-v4.ts`, `diktat-static-visual.ts`, `diktat-print-readiness.ts`, `lib/bundle/product-validator.ts`, `product-diktat-pdf.ts`, `product-v4-verification.ts`, `product-v4-verification-service.ts`, `product-v4-review.ts`, and the [system design](../../plans/article-diktat-authoring-system-design.md). Operational acceptance and chapter rollout remain tracked separately from this active contract.

## Replacement and readiness

All Product profiles require `expectedPreviousChecksum` for replacement at the shared staging service. MCP restaging carries the caller's `expectedRevision` unchanged; submission without it is create-only when the bundle ID differs in content. Readiness is scoped to the current publisher, including bundle and section decisions and live source dependencies. Publication holds share locks on referenced Ideas, sources, excerpts and external Product dependencies until commit. Import listing evaluates one artifact at a time to bound concurrent memory use.

V4 verification checks the actual staged chapter and original staging run before attaching an attempt. Missing read or stage scope returns an OAuth `insufficient_scope` challenge with the required scope. Local Playwright attempts require the local operator to execute them; polling does not start a hosted worker.

External Product dependencies must still be published under their transaction share locks. V4 readiness and publication apply the same stored-review validation against the current plan, signed receipt and section hashes. A new verified receipt requires a matching review.

Dependency lookup shares the canonical Product version-ID mapping with publication and runtime verification: version 1 uses the logical ID, later versions use `id:vN`. Live blueprint dependencies use their `approved` status; other Product dependencies require `published`. Retired entries fail verification.

MCP draft discard uses `authoring.discard_product_draft` with the verified product `runToken`, `bootstrapToken`, `importId` and caller-observed `expectedRevision`, plus `authoring:withdraw`. It rejects stale revisions, other chapters and assessment profiles. Admin item review and draft deletion also submit the displayed checksum. Shared content-addressed artifacts are retained until safe cleanup.

Readiness and publication select the same PDF evidence row for the current Article and Diktat lineage. V4 additionally requires the current plan, attempt, signed receipt, print profile, page count and exact receipt artifact key; attachment must succeed before verification completes. A canonical Diktat version with a different existing file key is a version conflict and requires a new reviewed version. Legacy Article-owned PDF fallback follows the same selection policy in both gates.

Local Product verifier launchers share one machine lock across imports, checkouts and legacy/V4 profiles, including capability discovery. The lock is acquired before bundling; each launch uses a private temporary module and cleans it up on exit. If a process is forcibly killed, first verify that no operator remains, then remove the per-user `zyx-product-local-<uid>.lock` directory under the operating system temporary directory before retrying. Per-import locks still protect the exact V4 attempt.

The Admin hides legacy PDF rendering for V4 and directs the reviewer to trusted verification. The Admin PDF POST route does not enqueue legacy rendering for V4. It returns `PRODUCT_V4_TRUSTED_VERIFICATION_REQUIRED` with recovery guidance to run trusted verification. PDF GET requires the exact `productId` and `expectedRevision`, and serves only the evidence bound to the current trusted receipt, plan, profile and page count.

Run adoption locks the import row before reading its staging audit. It rechecks draft status, checksum, object identity, course, version and validation report under that lock. A concurrent restage or adoption cannot overwrite the newer report or clear its reviews.

All Product staging, replacement and run-adoption audits receive a strictly increasing timestamp under the import or bundle-creation lock. Equal or skewed process clocks cannot reorder the current staging identity read by MCP and local operators.

Idempotent staging retries return success only after locking and rereading the requested import identity and checksum; a concurrent replacement or discard returns a stale-context conflict. The synthetic local fixture harness supplies an in-memory staging identity and exact PDF attachment selection. Its reports do not establish canonical database promotion or trusted deployed verification.
