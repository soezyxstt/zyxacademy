# Product Bundle V5

Withdrawal uses `authoring.withdraw_product_bundle` with the observed checksum, fresh bootstrap and bound run. Explicit `recovery: "exact_import"` permits withdrawal-only recovery without a run or Source Pack, with validated import/course identity. The shared service rechecks the import snapshot under its transaction lock. The Admin withdrawal API also requires that checksum; no Admin website visit is mandatory.

Status: `ACTIVE`, local source contract. V5 is an always-on, standalone learning profile. It does not alter V2 assessment solutions or V3/V4 Article and Diktat gates. Local implementation and generated migration do not establish deployment or live publication.

## Envelope and validation

The manifest uses `product-bundle.v5`, the ordinary Product manifest and ZIP checksum rules, and exactly one product. Its `productType` is `solution_collection` and its `schemaVersion` is `solution_collection.v1`. The product has the existing Product identity, version, status, creator, Idea links, source references, source hash and generation hash, plus required `chapterId`, `title` and `collection`. The collection uses the strict schema in `lib/materials/solution-collection.ts`, including `release: released_learning_content`. Its ID, title, course ID and chapter ID must match the enclosing product. Course and chapter titles must also match the current canonical records at publication. The collection schema permits an empty reader state, but V5 rejects an empty collection.

`generationHash` is SHA-256 of `deterministicProductSerialization` of the parsed product without `generationHash`. Dependencies must all target that exact product ID, version and hash. Each declared Idea and source material requires a matching `UP_TO_DATE` dependency with its version and hash; unrelated or product dependencies are rejected. Each source reference contains the source version, checksum and excerpt IDs. Publication rechecks active source materials, excerpt ownership and version, published Idea versions and hashes, and course scope under transaction locks. The review of problem and solution provenance is separate from these machine references and does not establish rights automatically.

Draft replacement calls `stageProductBundle` with the previously read checksum as `expectedPreviousChecksum`. A changed or missing previous checksum is rejected. Content-addressed uploads from a failed concurrent V5 stage can remain as unreferenced private objects; no automatic cleanup may delete an object another successful retry references.

The structured collection contains authored prompts, options, typed answers, strategy, ordered operations and reasons, verification, and separate problem and solution provenance. It is independently released learning content. It does not retrieve or expose solutions from an assessment or question bank. Every `code_example` explicitly sets `runnable: false`. Coding exercise locators, runnable examples and unsupported or unsafe payloads are rejected. Source figures are rejected until a dedicated access-controlled delivery implementation exists. Other visual definitions use the shared typed visual contract.

Draft discard through `authoring.discard_product_draft` requires `runToken`, `bootstrapToken`, `importId` and the caller-observed `expectedRevision`, plus `authoring:withdraw`. The verified learning-product run must match the course and chapter. A stale checksum is rejected before deletion. Admin draft deletion and item review likewise send the displayed checksum. Shared private artifacts remain until reference-aware cleanup.

## Headless review and publication

No Admin website visit is required. An authenticated, appropriately scoped MCP or API handler must derive the actor from its session or principal and use the same admin-equivalent authorization as the existing Product publication service. Never accept an actor ID supplied by a caller as proof of authorization.

### Automation: prerequisite Ideas and consent

The Source Pack to V5 pipeline first publishes its Idea Bundle. After staging, obtain its checksum with `authoring.get_import`, then call `authoring.get_idea_review_context` with the Idea-stage bootstrap token, locked `idea_product` run token, import ID and `expectedRevision`. Inspect the actual Ideas, provenance, relations and sections. `authoring.review_idea_revision` records the explicit decision and item hash for every Idea, together with the bundle decision, for that exact checksum. Approval requires every item approved. It does not infer item decisions. The same admin calls `authoring.publish_idea_bundle` with the same run, bootstrap, import and checksum. It checks the stored item decisions, revision-bound review evidence, approval, actor, artifact and transaction snapshot before publishing; retrying a published matching revision is idempotent. A stale revision fails. The older `authoring.review_idea_bundle` records only a bundle-level decision and is insufficient for this headless path. Its original reviewer can explicitly reaffirm that same decision and notes with current item decisions through `authoring.review_idea_revision`; the original decision remains immutable.

OAuth defaults deliberately omit `authoring:publish`. If an OAuth tool call lacks a scope, the MCP tool error includes `mcp/www_authenticate` with an `insufficient_scope` challenge and the required scope. Reauthorize the same client using the advertised authorization server and resource, authorization code with S256 PKCE, and a `scope` parameter containing the union of its current scopes and `authoring:publish`. The admin must approve the requested scopes on the consent screen; exchange the code for a new token and retry. A new consent grant replaces the previous scope set for that client, session and resource, so retain every scope still needed. A client that cannot process the challenge must initiate this authorization flow explicitly. Consent does not replace the active-session and admin checks.

The existing manual connection endpoint issues all authoring scopes, including publication, to an authenticated admin session; a direct authenticated session likewise has all authoring scopes. These paths intentionally retain that privilege decision and do not use a separate OAuth consent record. MCP authentication requires a live session and active canonical admin membership. Idea and Product lifecycle services check the active canonical identity and required membership again for the explicit actor, including retries, and lock those rows in each write transaction. Headless Idea revision review, V5 review, and Idea and Product publication also retain the existing requirement that the legacy `user.role` is `admin`. Scoped tutor reviews require active canonical tutor membership and the existing course access check. Their transaction holds a shared lock on the tutor user row. Canonical assignment writers and legacy assignment replacement take an exclusive lock on that same row before mutation, including when no canonical assignment exists and access uses the legacy fallback. Role changes through Admin actions, Admin MCP and Admin Ops acquire the user row before the canonical identity and membership mutations, matching the authoring lock order. Role and legacy-role changes commit atomically. Admin API routes reject suspended accounts even when their session and legacy role remain valid. No actor identity can be supplied by the MCP caller.

1. `getSolutionCollectionReviewContext({ importId, reviewerId, expectedRevision })` returns the exact staged checksum as `revision`, an opaque reviewer-specific `reviewVersion`, the complete collection, and a hash for each item. Only a current draft is reviewable. The Admin GET requires `?expectedRevision=<displayed checksum>` and passes that revision through the service snapshot checks. A failed or mismatched context response never replaces the last valid client baseline or its pending draft. Review and publication controls remain disabled while context is unresolved; navigation still warns about unsaved work, including when tab storage is unavailable.
2. `reviewSolutionCollection({ importId, reviewerId, expectedRevision, expectedReviewVersion, decision, items })` accepts one decision per exact item ID and hash. Each decision explicitly supplies `correctness`, `reasoning`, `problemProvenance`, `solutionProvenance`, and `release`, each `approved` or `changes_requested`, with optional notes. `expectedReviewVersion` must echo the context token. The server compares it under the import lock before changing a decision, so an already-open stale tab cannot overwrite another save. A conflict returns `PRODUCT_V5_REVIEW_STALE`; reload context and explicitly resolve local changes before retrying. Identical decision retries remain idempotent. Each changed save receives a fresh token, including a return to earlier decisions. Approval requires every field on every item to be approved. Correctness covers the prompt and answer. Reasoning covers strategy, justified steps, verification, and the spoiler-free nature of any hint. Release covers rights and suitability for learner access. The full item hash binds all these fields and both provenance records. A rejection may contain changes requested. The server claims the unchanged draft in a transaction, stores the complete decision, and audits changes. Identical retries return the existing decision without a duplicate audit; a changed decision is allowed only while the same revision remains a draft.
3. `publishProductBundle({ importId, publishedBy, expectedRevision })` requires the same admin actor's approved full-item review, the exact current checksum, active source and Idea checks, matching course and chapter, and all locked dependencies. It repeats review validation and claims the snapshot inside the transaction. The canonical collection, import state, publication record and audit are committed together. An identical publication retry returns the existing publication with `published: false`; an old checksum fails. The V5 path has no Article, Diktat, PDF or V4 verification requirement.
4. `withdrawProductBundle({ importId, withdrawnBy })` atomically withdraws the collection and import and records the action. A withdrawn version remains for audit and is not served to learners. Only one version of a product may be published at once; withdraw an old version before publishing another.

Review is an explicit authorization to release, not proof of mathematical correctness, source rights or absence of copied protected assessment material. Operators must inspect all items and make those decisions. There is no automatic live dependency invalidation or re-review after publication; when a source or Idea changes, operators must assess and withdraw or revise affected collections. Versioned dependency and trace metadata are stored with the collection for that purpose.

## Learner boundary

`listPublishedSolutionCollections({ courseId, userId })` returns metadata only for active, published and accessible course/chapter records. `getPublishedSolutionCollection({ courseId, collectionId, userId })` rechecks the same authenticated course entitlement and free-chapter policy, validates the stored collection and returns `null` for absent, invalid or inaccessible content. The ID for detail reads is the catalogue row ID, including its version suffix where applicable. Both use the central course-access policy. No collection is added to Article, quiz, Zyra, search or vector indexes. Publication and withdrawal do not enqueue vector work.

The generated PostgreSQL migration is additive and must be applied separately to an explicitly verified target. Synthetic tests do not establish database transaction behavior, staging authorization, installed MCP tools, deployed routes, learner visual behavior or live storage success.

The optional Admin review surface restores the current reviewer's saved decisions for the exact revision. Partial decisions are recoverable within the same browser tab, scoped to the authenticated reviewer and import, and retained only for server-confirmed unchanged item hashes. A tab draft records the server review baseline. A newer server review wins and triggers an explicit conflict choice; saved submissions clear their tab copy. Unsaved in-memory decisions remain available for explicit conflict recovery even when tab storage is unavailable. This protects a stale save while the component remains open; blocked browser storage cannot guarantee recovery after a reload. Browser drafts never grant publication permission; the full review must be explicitly submitted to the server.

Correctness and reasoning are independently required persisted decisions. Earlier review rows without the reasoning field fail the current review validator and need a fresh review. The optional Admin UI blocks publication while local review changes differ from the saved approval and offers explicit restoration. Completion markers and the next incomplete item action support long reviews. An optional `hintMarkdown` is authored separately from the full strategy. It is a short starting clue, limited to 1,200 characters of text and inline math, without fenced code, HTML or embedded images. It must not identify the final answer, correct option, complete derivation or solution code. The Admin review displays the authored hint beside the item decisions even while the solution is expanded. The reasoning decision explicitly reviews this semantic constraint; structural validation alone cannot prove it. Without an authored hint the reader shows no hint control, and never exposes strategy before the full solution. The item hash binds any hint, so changing it requires review of the new revision.

The Admin V5 detail keeps the review component mounted during detail refresh, including when tab storage is unavailable. A stale bundle checksum refreshes the parent detail and then reloads review context. Local decisions apply only to item hashes confirmed unchanged by the server; changed items require a new decision. Unsaved notes and decisions for changed or removed items remain in a read-only recovery field until explicitly discarded. They cannot approve the new content. Discarding earlier-item drafts preserves any separate unresolved conflict for unchanged items and its original saved-review baseline. Review and publication stay blocked while those earlier drafts await resolution. Semantic comparison against the saved baseline ignores whitespace-only notes and edits returned to their saved values. A refresh of the saved review alone still uses the independent review-version conflict check.

During review-context refresh, the last visible decisions remain displayed with editing disabled and a loading status. Tab-storage availability is reported separately from draft recovery, so the warning remains visible after an in-memory recovery. A full server save still requires every item decision.

`authoring.get_solution_collection_review_context` requires the caller-observed `expectedRevision`, as do review and publication. Scope validation binds the import row and parsed V5 checksum, course and chapter; the services claim the same row identity and revision under the import transaction lock. A changed revision, source identity or scope returns a conflict and requires fresh context. The generic scoped Product publication tool applies the same V5 guard.

The user-row lock precedes identity and membership writes. The identity row uses `FOR NO KEY UPDATE`, which conflicts with authoring shared locks while allowing foreign-key key-share checks, following the [PostgreSQL row-lock compatibility rules](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS). This does not replace a real multi-session contention check.

Browser Back and Forward between tracked question entries in the same mounted review preserve its drafts without a leave warning. The exception allows only a changed `item` parameter with the same route, hash and remaining query parameters. Pending operations, untracked history entries and navigation away from the review retain their guards.
