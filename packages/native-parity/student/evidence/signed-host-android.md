# Signed Student host on Android API 35

The integrator already owns a signed mounted-app rehearsal. At parent `ecf50dd0`, the existing Native integration preview manual run enables the authenticated Android job, restores the exact `mounted-product-sources` tree, builds the disposable loopback APK and starts the real product auth handlers with runner-local PostgreSQL 17 and HTTPS. The authenticated emulator is API 33. The sibling product-entry job uses API 35 to check guest routing.

1. Compose the four lanes with `scripts/native-readiness/preview-lanes.sh` in a disposable checkout. Run `python3 scripts/native-readiness/product/mount.py` and record the staged tree as the integrator workflow does. The reviewed composition of host `ecf50dd0`, Student `02579f6f`, Shared UI `4805e7d1`, Academic `5b16638c` and Operations `332a4d0a` mounted 153 canonical routes, including 50 Student-owned routes, and the `/murid` redirect. Staged tree `dcf4c297f36f8f0ad4b42567db304ed734434ae7`.
2. Reuse `native-authenticated-preview.yml` and its Android build and run scripts. The integration change is an API 35 Google APIs x86_64 emulator with the isolated fixture CA trusted by its Chrome process. The existing app overlay trusts the fixture CA only at `https://127.0.0.1:9443`. The emulator script installs that CA into `/system/etc/security/cacerts`. Verify Chrome's active trust store on the API 35 image before using the same script. The existing `/__preview/health` Maestro check and server observation are the acceptance gate for both browser navigation and TLS trust.
3. Run the existing `.maestro/native-integration/authenticated/student.yaml`. Its entry is `zyx-native-parity://sign-in?next=%2Fdashboard&locale=id`. Expect native browser handoff and code exchange, a verified `murid` context, `student-dashboard-preview`, one owned unread inbox notification, selected acknowledgement and sign-out. Reopen `zyx-native-parity://dashboard` and require sign-in again. The backend also verifies the other Student's notification remains unread and the session is revoked.
4. The signed server currently dispatches `GET /api/native/student/courses?view=dashboard`, `GET /api/notifications/history` and `PATCH /api/notifications/read`. Signed catalog, enrolled course or PKA device proof would need narrowly dispatching their real production handlers and seeding the corresponding Student access in the same disposable backend.

The exact device cannot run in this workspace, which has no Android emulator or KVM. The existing authenticated runbook covers the hosted fixture, and the installed APK and browser are needed for the API 35 claim.

The local loopback rehearsal passed with Bun 1.3.14 and disposable PostgreSQL 17.12. The official `AUTH_STUDENT_PRODUCT=true` smoke used the mounted tree above and verified start, completion, exchange, signed session, Student context, dashboard, recipient-scoped inbox acknowledgement and logout. The fixture database and TLS material were removed at the end. This was a protocol and backend test, with no APK or browser simulator running.
